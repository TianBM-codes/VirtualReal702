# 近期效率优化与算例总览

更新时间：2026-09-23
范围：超大 BDF/OP2 导入、结果切换、模态振型/动画、法向量计算、缓存与 A/B 测试工具。

## 1. 总体结论

近期优化主要解决了三类问题：

1. **首次导入超大模型容易慢或内存不足**：针对结构简单的大型壳模型，增加 BDF 流式快速路径，避免 pyNastran 为约 200 万节点、200 万单元创建大量 Python 对象；同时在 OP2 导入时，若已确认全部节点 `CD=0`，不再重新读取整份 BDF。
2. **结果反复切换仍重复计算和读取**：位移、渲染数组、变形法向量以及最终二进制响应增加分层缓存；法向量默认尝试 PyVista/VTK，失败时自动退回 NumPy。
3. **大模型云图计算耗时高**：合入 `perf/frame-scalars-cache` 的 ELEMENT_NODAL 全向量化、标量结果两级缓存和自动预热，用户模型的 `frame-scalars` 冷算记录由约 2 分钟降至 21.36 s。
4. **L2 邻接关系受 Python 循环限制**：共享边生成改为 NumPy 批量分组，均化域划分改用 SciPy 稀疏图连通分量；L3 临时调整特征角时复用同一算法思路。

在当前 200 万节点圆柱算例上：

| 阶段 | 优化前 | 优化后 | 新版占旧版 | 提升 | 加速倍数 |
|---|---:|---:|---:|---:|---:|
| BDF L1 打包 | 143.6 s | 54.5 s | 38.0% | 62.0% | 2.63x |
| OP2 打包 | 111.1 s | 8.5 s | 7.7% | 92.3% | 13.07x |
| L2 几何预处理 | 无严格同条件基线 | 98.14 s | - | - | - |

这里的 OP2 提升主要来自**跳过第二次超大 BDF 读取**，不是 OP2 文件本身缩小。BDF 快速路径同时降低了 pyNastran 对象模型导致 `MemoryError` 的风险。

## 3. BDF 导入优化

### 3.1 原问题

旧流程统一调用 pyNastran 读取 BDF，并建立完整对象模型。另一台电脑解析 200 万节点模型时，报错位置为 pyNastran 向 `_type_to_id_map[elem.type]` 追加单元 ID，最终触发 `MemoryError`。这说明主要问题不是 BDF 语法，而是数百万节点和单元对应的 Python 对象、字典和列表占用过高。

### 3.2 当前实现

`src/l1/bdf_pack.py` 增加大型 BDF 的流式快速路径：

- 默认只对不小于 100 MiB 的 BDF 自动尝试，阈值由 `APP_FAST_BDF_MIN_BYTES` 调整。
- 逐行读取文件，不构造 pyNastran 的完整节点/单元对象图。
- 当前支持 `GRID`、`CQUAD4`、`CTRIA3`、`PSHELL`、`MAT1`。
- 直接生成现有 L1 HDF5、`assembly.h5`、集合、节点到单元 CSR 和 `manifest.db`，因此 L2 和 L3 无需改接口。
- 在 `l1_meta` 中记录 `source_bdf_path`、`bdf_fast_path=1` 和 `bdf_all_cd_zero`。
- 不符合快速路径条件时，自动回退原 pyNastran 流程。

配置方式：

```text
APP_FAST_BDF=auto     # 默认，大文件尝试快速路径
APP_FAST_BDF=force    # 强制使用；不支持时直接报错，适合测试
APP_FAST_BDF=0        # 禁用，完全使用旧路径
```

### 3.3 保守回退条件

以下情况不会冒险走当前快速路径：

- `INCLUDE`；
- 节点输入坐标系 `CP != 0`；
- `CORD1*`、`CORD2*`、`GRDSET` 等坐标系卡；
- 梁、实体或其他尚未覆盖的几何单元；
- 长字段格式的关键几何卡；
- 没有找到节点或受支持的壳单元。

因此该优化目前最适合“超大、规则、全局坐标下的三角形/四边形壳模型”，并不是完整替代 pyNastran。

## 4. OP2 导入优化

旧流程读取 OP2 后，为了把节点位移从节点输出坐标系 `CD` 转回全局坐标，又通过 pyNastran 重新读取一次配套 BDF。对 221 MiB 的 BDF，这一步反而成为 OP2 导入的主要耗时和内存来源。

现在 BDF 快速路径会扫描并记录所有节点是否满足 `CD=0`。`src/l1/op2_pack.py` 读取到 `bdf_all_cd_zero=1` 后：

```text
CD transform: manifest says all nodes CD=0 (global), skip BDF reread.
```

此时位移已经位于全局坐标系，可以安全跳过 BDF 重读。若没有该标记或存在非零 `CD`，仍执行旧的坐标转换流程，不牺牲结果正确性。

## 5. 结果切换与法向量优化

### 5.1 分层缓存

当前结果链路包含以下缓存：

| 层级 | 内容 | 位置/策略 |
|---|---|---|
| 原始位移缓存 | 指定结果组、step、frame、instance 的节点位移 | `l3_cache/raw_displacements/*.npy` |
| 渲染数组缓存 | 不变的 positions 和 indices | 进程内 LRU，默认最多 4 项；`APP_L3_RENDER_ARRAY_CACHE_MAX` 可调 |
| 变形法向量缓存 | 指定 frame、scale、result group 的 normals | `l3_cache/deformed_normals/*.npy` |
| 变形响应缓存 | positions、normals 和辅助几何打包后的完整 L3BE | `l3_cache/deformed_payloads/*.l3be` |
| 模态振型缓存 | 单阶模态位移的完整 L3BE | `l3_cache/modal_payloads/*.l3be` |
| 模态动画缓存 | 指定阶次、scale、帧数的完整动画二进制 | `l3_cache/modal_payloads/*.bin` |

缓存 key 包含模型、instance、step、frame、scale、result group，并结合渲染文件和结果文件的大小/修改时间。源文件变化后会生成新 key，避免直接复用旧结果。

接口通过响应头返回 `X-Cache: hit` 或 `miss`，便于前端和测试脚本判断命中情况。

### 5.2 法向量计算

变形后的法向量现在由后端计算并随 `deformed-positions` 一起返回：

- 默认 `APP_L3_NORMAL_BACKEND=pyvista`，调用 PyVista/VTK 的 `compute_normals`；
- PyVista/VTK 不可用或运行失败时自动退回 NumPy；
- NumPy 版本使用三角面叉积和 `np.add.at` 累加；
- 计算后的 normals 落盘缓存，相同变形状态不再重复计算；
- 前端只要消费接口中的 `normals` section，就不需要再次执行 JS `computeVertexNormals()`。

需要注意：当前 viewer 中仍有若干 `computeVertexNormals()`，用于初始几何、局部功能或后端未返回 normals 时的回退。正式前端接入时仍需确认主模型加载、模态同步等路径是否确实优先使用后端 normals。

### 5.3 `frame-scalars` 向量化、缓存与预热

从 `perf/frame-scalars-cache` 合入的优化覆盖云图主链路：

1. `_en_per_vertex_averaged` 将原来的逐三角形 Python 循环改为 NumPy 分组、排序和 `reduceat`，保留按单元类型、域和节点执行 75% 条件平均的语义。
2. 归一化前的 `scalar_vertex`、图例范围和全模型范围进入统一缓存。缓存 key 包含结果文件 `mtime_ns + size`、instance、帧、分量和渲染参数，结果文件重写后自然失效。
3. 内存层是按总字节数淘汰的进程内 LRU；磁盘层位于 `<workspace>/l3_cache/scalars` 和 `ranges`，重启后仍可复用，多 worker 也可共享。
4. 新增后台自动预热：模型 render-ready 或检测到新 result group 后，串行预计算各 step、field、instance 的第 0 帧默认视图和范围。
5. 新增手动预热接口：`POST /api/odb/{odb_id}/results/warmup`。历史老模型不做启动时全量回填，需要时手动点名。
6. 变形家族复用同一套 LRU/磁盘设施：缓存变形整包、顶点位移、suggest-scale 统计；modal-shape、vertex-displacements 和 modal-animation 共用顶点位移。

默认配置：

```text
APP_SCALAR_CACHE_MB=512         # 每个 worker 的内存结果缓存；0=关闭结果缓存
APP_SCALAR_DISK_CACHE_MB=2048   # 每个 workspace 的磁盘缓存；0=仅内存
APP_WARMUP=1                    # 自动预热；0=关闭自动预热，手动接口仍可用
```

合并时统一了开关语义：`APP_SCALAR_CACHE_MB=0` 时，内存与磁盘结果缓存都不读写；避免出现“配置声明关闭，但仍从磁盘命中”的情况。

已有性能记录：

| 场景 | 优化前 | 向量化后 | 提升 | 加速倍数 |
|---|---:|---:|---:|---:|
| 用户 700～800 万面片 S 场 `frame-scalars` | 约 120 s | 21.36 s | 约 82.2% | 约 5.62x |
| 本机合成 200 万面片 | 50.5 s | 5.7 s | 约 88.7% | 约 8.86x |

这两组数据主要反映**冷计算向量化**收益。内存命中、磁盘命中、服务重启后首次命中和自动预热效果仍应在目标机器上用同一模型补测。

## 6. L2 邻接关系优化

L2 需要先找出共享网格边的表面单元，再根据截面、单元类别和法向夹角划分均化域。旧实现逐面、逐边执行 Python 循环，并用 Python 并查集逐条合并；模型越大，解释器开销越明显。

当前实现保持 HDF5 schema 和计算规则不变，只替换计算方式：

- NumPy 一次性展开三角形、四边形等表面的边，并按节点对排序分组；
- 普通流形边（恰好两个面共享）完全批量化，罕见的非流形边才保留小循环；
- 根据截面、实体/壳/膜类别和特征角批量筛选可连接边；
- 用 `scipy.sparse.csgraph.connected_components` 在稀疏邻接图上求连通分量；
- 按每个连通域首次出现的元素重新编号，保持 `domain_id` 稳定；
- L3 动态修改特征角时也使用 SciPy，降低首次请求的 CPU 时间。

这项优化发生在后端 CPU，不增加前端显卡负担，也不改变节点、单元、面、夹角或均化域的物理含义。实际收益取决于表面面数和共享边数量，需要用 `tools/benchmark_versions.py` 在 50 万节点圆柱模型上重新跑新旧版本确认。

## 8. 接口与网络实测

以下为 200 万节点算例的本机记录。服务端耗时来自 `X-Elapsed-Time-Ms` 或服务计时，HTTP 总耗时包含完整响应体传输和客户端读取。

| 功能 | 响应量 | 首次服务端 | 缓存命中服务端 | 首次 HTTP 总耗时 | 命中 HTTP 总耗时 |
|---|---:|---:|---:|---:|---:|
| 模型 `render-buffers` | 144.8 MB | 277 ms | 未单列 | 365 ms | 未单列 |
| `modal-shape` | 96.5 MB | 601 ms | 43 ms | 706 ms | 121 ms |
| `deformed-positions` | 193 MB | 2,862 ms | 234 ms | 3,030 ms | 457 ms |
| `modal-animation`，4 帧 | 386 MB | 1,936 ms | 450 ms | 2,210 ms | 840 ms |

这些数据说明：缓存已经明显降低服务端重复计算，但**缓存命中后仍需把整个响应重新传给前端**。网络传输并没有因为服务端落盘缓存而消失。

按当前格式，模态动画 20 帧预计约 1.93 GB，不适合每次切换都整体下载。对于远程部署，后续更值得做的是：

1. 模态振型只传一次位移向量，在 GPU shader 中按相位播放；
2. positions、indices 等静态几何只下载一次；
3. 结果切换优先传节点位移或标量，避免反复传完整 positions + normals；
4. 需要大动画包时考虑分块、压缩、HTTP/2，并设计前端内存上限。

## 9. 新旧版本计时工具

统一脚本：`tools/benchmark_versions.py`。它通过现有 HTTP 接口观察项目状态、读取阶段日志并模拟前端请求，不需要侵入业务代码。

支持的测试项：

- BDF 项目从 pending/running 到 ready；
- 日志中的 `l1_bdf`、`l2_ingest`、`rg_op2` 阶段；
- metadata、模型加载、模态振型、变形位置、模态动画；
- 首次请求、重复请求中位数、P95、响应大小、`X-Cache` 和服务端耗时；
- CSV 原始数据和 Markdown 对比报告。

当前实际使用场景是新旧程序共用同一端口，应采用：

```powershell
python tools\benchmark_versions.py `
  --config tools\benchmark_versions.json.example `
  --mode sequential
```

脚本先监控并测试旧版，立即保存 checkpoint；随后持续轮询，等待旧服务关闭、新服务在同一端口启动并创建另一个项目，最后完成新版测试和汇总。两个版本应使用同一 BDF/OP2、相同前端操作和不同项目 ID。

## 10. 当前边界与风险

1. BDF 快速路径只覆盖有限壳模型子集；复杂模型仍走 pyNastran。
2. 首次导入仍然需要完成 BDF L1、L2 和 OP2 打包，当前优化重点是避免异常内存和重复工作，不是让首次导入瞬时完成。
3. 落盘缓存会增加项目目录占用，尤其是多个 scale、frame 和动画帧数组组合。
4. 当前缓存读取使用完整 `bytes`/NumPy 数组，超大缓存命中仍会产生内存和磁盘 I/O 压力。
5. 服务端缓存不能替代网络协议优化；跨机器访问时，193 MB 或 386 MB 响应仍可能成为主要瓶颈。
6. viewer 不是最终前端，最终效果必须在甲方实际前端确认是否使用后端 normals 和模态位移接口。
7. 当前 L2 的 98.14 s 没有同机器、同条件、同版本顺序下的严格旧版对照，不应据此声称 L2 获得提升。
8. 默认每 worker 512 MiB 内存缓存，多 worker 会各占一份；需要按部署 worker 数量评估总内存。
9. 自动预热会把部分首次等待转移到后台任务，模型刚 ready 时会增加一段 CPU、磁盘和缓存写入负载。

## 11. 建议的下一轮验证

按优先级建议：

1. 在目标电脑使用 `sequential` 脚本完成一次严格 A/B，对 BDF、L2、OP2、模型加载、模态切换和动画分别出报告。
2. 同时记录 Python 进程峰值工作集，确认新版在低内存机器上不再触发 `MemoryError`。
3. 使用 Chrome Performance 或正式前端埋点补充“收到响应后到首帧显示”的时间，后端脚本无法测 GPU 上传和 Three.js 渲染。
4. 优先把正式前端调整为“静态几何一次加载 + 模态位移一次传输 + GPU 动画”，避免 20 帧约 1.93 GB 的动画包。
5. 若仍需降低首次导入内存，再将 BDF 快速路径改为分块 HDF5 写入，并分块构建节点到单元索引。
6. 对 `frame-scalars` 分别记录冷计算、内存命中、清内存后的磁盘命中、重启服务后的首次命中和预热完成后的首次点击。
