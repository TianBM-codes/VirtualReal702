# UNV 支持现状与生成规划

更新时间：2026-07-28

## 1. 这次先解决了什么

这次不是只补一个 dataset，而是先把 `UNV` 的“地基”补稳了：

1. 统一了底层读取入口，新增 `services/model_update/importers/unv_utils.py`
2. 读取方式从“整文件一次性读进内存”改成了“按 dataset 分块流式读”
3. 增加了编码识别和逐行兜底解码，重点照顾包含中文标题/说明行的 `UNV`
4. 在现有导入链路上补了 `dataset 151 / 164` 的结构化识别

这样做的目的很直接：

- 大文件时，先不把整个 `UNV` 一次性塞进内存，风险更低
- 中文不再简单 `errors="ignore"` 吃掉，信息不容易丢
- 后面如果接 `pyuff` 做写出，不用再改业务层入口

## 3. 为什么这次没有一步到位改成 pyuff

用户需求里提到“最好用 `pyuff`，后面可能还要生成 `UNV`”。这个方向我认同，但这次没有直接硬切，原因是：

1. 当前仓库还没有 `pyuff` 依赖，直接切换会把这次修复和依赖变更绑死
2. 现有导入链路已经和自研解析结构耦合，立即全量替换风险较高
3. 这次更紧急的问题其实是“大文件 + 中文 + 常用 dataset 漏支持”，先把入口稳定下来更划算

所以这次采用的是“先把接口层整理干净，再给 `pyuff` 留接入口”的做法。

## 4. 后续生成 UNV 的建议计划

建议分三步做，不要一步把“读”和“写”同时重构。

### 第一步：收口数据模型

目标：把程序内部真正需要的 `UNV` 信息，整理成统一中间结构，而不是直接依赖“某个 parser 返回什么字典”。

建议抽象：

- `UnvNodeBlock`
- `UnvCoordinateSystemBlock`
- `UnvTraceLineBlock`
- `UnvModalBlock`
- `UnvFrfBlock`
- `UnvMetadataBlock151`
- `UnvUnitsBlock164`

收益：

- 以后不管底层是自研 parser 还是 `pyuff`，上层导入逻辑都不用改
- 将来“写回 UNV”时，直接从统一结构生成，而不是从数据库字段反推

### 第二步：引入 pyuff 做写出优先

目标：先让 `pyuff` 承担“生成 UNV”的职责，而不是第一天就接管全部读取。

建议优先写出这些 dataset：

1. `15` 或 `2411`
2. `82`
3. `55`
4. `58`
5. `151`
6. `164`

原因：

- 生成 `UNV` 对格式正确性更敏感，`pyuff` 更适合做这件事
- 写出链路比读入链路更容易做闭环验证

建议输出场景：

1. 从模态数据库导出试验模态 `UNV`
2. 从 FRF 数据库导出 `dataset 58`
3. 导出带中文标题/说明的 `UNV`，统一用 `utf-8` 或明确指定编码

### 第三步：逐步让 pyuff 接管读取

目标：不是“全部替换”，而是“分 dataset 替换”。

建议顺序：

1. `151 / 164`
2. `58`
3. `82`
4. `2411 / 2420`
5. `55`

原因：

- `151 / 164` 目前还只是结构化识别，最适合作为第一批切换目标
- `58` 有较固定的曲线结构，也适合单独验证
- `55` 关系到模态/静力导入主链路，放最后风险最小

## 5. 大文件与中文的专项建议

### 大文件

这次已经先做了“按 dataset 分块读”。后面如果仍然遇到超大 `UNV`，建议继续做：

1. `dataset 55 / 58` 按块边读边落库，不在 Python 内存里长期保留全部结果
2. 对仅用于入库的路径，避免同时构造 `nodes + elements + tracelines + full modes` 四套大对象
3. 对非常大的 FRF，优先流式插入数据库，而不是先拼完整 Python 列表

### 中文

这次已经做了：

1. 编码探测
2. 逐行兜底解码
3. 去掉了原来 `utf-8 + ignore` 那种容易静默丢字的读法

后面建议再统一约定：

1. 新生成的 `UNV` 默认写 `utf-8`
2. 数据库存 `title / extra_json` 时统一 `ensure_ascii=False`
3. 如果外部软件只能吃本地编码，再在导出层显式指定 `gb18030`
