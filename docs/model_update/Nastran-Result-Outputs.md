# Nastran Result Outputs

这份说明只回答一个问题：Nastran 结果在当前项目里最终会以什么形式落地。

## 三种输出

当前实现把 Nastran 结果分成三种输出，目的不一样：

1. API JSON  
给前端和 APIfox 调试用。优点是直观、容易看字段，也方便把预览接口和真正入库接口拆开。

2. 数据库记录  
给项目后续的查询、比对、参数管理和业务流程复用。模态结果继续复用现有模态入库链路；BDF 材料、属性等基础信息保留原来的入库能力，不做删改。

3. VTU 文件  
给后处理可视化用。这里的“后处理”按当前约定，就是把结果导出成 `vtu`，方便在 ParaView 之类工具里直接看场分布。

## 各结果怎么映射

### 模态结果

- 输入：`SOL103` 产生的 `OP2`
- 解析：优先用 `pyNastran`
- API：提供模态预览、模态入库、模态 `VTU` 导出
- VTU：
  - 节点位移写成 `point_data`
  - 旋转自由度也保留在 `point_data`
  - 位移模长单独输出，方便直接着色

### 灵敏度结果

- 输入：`SOL200` 产生的结果文件
- 生成：`SOL200` 控制段和设计卡片优先参考 `femtools_bas` 里的 BAS 逻辑，而不是直接依赖 `pyNastran` 写卡
- 解析：当前先走 `pyNastran`/结果对象启发式读取，优先把矩阵预览、入库、`VTU` 导出链路打通
- VTU：
  - 目前按“单元灵敏度场”输出
  - 每个单元会根据参数映射关系挂到 `cell_data`

## 为什么要保留 BDF 基础入库

原有的 `BDF -> 材料/属性/节点/单元` 入库能力要保留，因为它不是历史包袱，而是后续很多功能的地基：

- `SOL200` 的参数映射需要知道材料和属性是谁
- `E`、`RHO` 这种参数本来就挂在材料上
- `H` 这种参数本来就挂在属性上
- 前端如果要做参数选择、结果解释，也需要先有这些基础数据

所以当前实现不是“新 Nastran 功能替换旧 BDF 入库”，而是“新功能复用旧基础能力，再往上叠加”。

## 工具选择

- `SOL103` / `SOL200` 输入卡改写：
  - `SOL103` 继续走现有 Python 实现
  - `SOL200` 明确优先参考 BAS 脚本逻辑
- `BDF` / `OP2` 读取：
  - 优先用 `pyNastran`
- `VTU` 导出：
  - 用 `meshio`

这样分工的好处是：

- BAS 负责提供经过业务验证的 Nastran 写卡经验
- `pyNastran` 负责提供 Python 侧稳定的 BDF/OP2 读取能力
- `meshio` 负责把后处理结果变成通用可视化格式
