# BDF/OP2异步调度与修正数据存储方案

日期：2026-10-15。

**本次范围**：实现独立`src/job_runner.py`的BDF/OP2自动修正导入异步调度和阶段日志。
用户要求存储调整先出方案，暂不实施；现有修正MySQL表、H5/NPZ格式和数值处理不迁移。

## 已实现的调度

此前200万模型在21:43:16完成BDF可视化，自动修正导入直到21:49:26才返回；OP2随后约18秒完成。
根因是主线程在调用修正导入时一直等待。页面的几何ready不等于该线程已经空闲。

```mermaid
flowchart LR
  B[BDF可视化 L1/L2] --> Q[记录BDF修正任务]
  Q --> O[主队列继续解析OP2]
  O --> R[OP2可视化就绪]
  R --> M[记录OP2修正任务]
  Q -.-> W[独立修正导入线程]
  M -.-> W
  W --> S[BDF修正导入先完成，再导入OP2修正数据]
```

- 主队列只写本地调度记录，不连接MySQL、不等待修正导入函数返回。
- `src/model_update_tasks.py`运行一个独立后台线程，修正任务内部仍依次执行，避免BDF清空数据与OP2写入交叉发生。
- 注册库新增`model_update_import_tasks`，只保存来源版本、阶段、状态、时间和错误，不保存节点或振型数组。这是调度元数据，不是修正数据迁移。
- 状态：`pending → running → ready/failed`；修正失败不把可视化ready改回失败。
- 来源路径、大小、修改时间、配置和项目身份参与去重。开始前检查项目与来源版本，过期任务不执行。
- 服务恢复后可继续排队任务；已中断的执行中任务标为`failed/interrupted`，不自动重跑，也不补跑历史项目。
- 删除和克隆保护覆盖pending/running修正任务；缓存预热也会让路。失败或完成后解除保护。
- 项目自动OP2修正导入统一异步，旧`modal_import.async_submit=false`兼容接收但不再阻塞可视化；独立修正API的同名参数不变。
- INP、CDB、RST等其他流程本次未改调度。旧`webapi.background_jobs`任务不自动复制进新队列。

独立线程仍共享CPU、内存和磁盘，不等于物理资源隔离；后台只开一个修正线程以限制资源叠加。
后续若需要更强隔离，再评估独立进程。本次不增加第三个手工启动服务。

## 已实现的日志

追加结果立即记录“已接收/排队”，主队列领取后记录“开始解析”。
`GET /api/projects/{project_id}/logs`保留旧字段，增加`pipeline`和`model_update_tasks`，增量日志为空时也返回实时状态。
日志窗分开显示“可视化解析”和“模型修正后台”。百分比称为“最近阶段进度”，不把几何100%解释成全部完成。

BDF修正阶段依次显示：检查数据库、读取BDF与节点、整理材料/属性/约束、整理索引输入、写MySQL、保存集合H5、构建并保存节点索引、登记配置、提交事务。
OP2修正任务区分读取/节点对齐与写入修正数据。长阶段每30秒写当前阶段和已用时，不虚构完成百分比。
历史日志仍可读，旧工作区没有新队列记录时返回空数组，不因此重新解析模型。

## 存储方案：仅建议，尚未实施

现状并非“全部节点都写MySQL”：材料、属性、约束、项目配置等在MySQL；集合成员明细已有`capability_details.h5`；节点匹配索引已有`*.node_octree.npz`；模态节点向量已有`cal/fem_modal_bundle/mode_*.npz`与清单。
旧自动OP2任务还返回完整节点payload，通用后台任务系统会再次转JSON保存到MySQL任务结果，形成重复的大结果记录。
新调度队列不保存这个返回体，但本次没有修改通用后台任务系统或已有修正数据。

建议“小目录入库，大数组入文件”，优先减少重复读取和转换：

| 内容 | 建议存储 | 原因 |
|---|---|---|
| 项目、材料参数、壳厚、约束、任务状态、文件版本索引 | MySQL小表，必要时批量写入 | 查询、事务和参数编辑方便 |
| 大量节点坐标、编号、单元连接、集合成员、各阶振型 | H5数据集；已有NPZ兼容读取 | 避免大量数据库往返；支持按帧/阶/节点分块读取 |
| 可视化已经有的几何和U结果 | 尽量只读复用L1 H5 | 不重复读取原始BDF/OP2，不重复复制相同数组 |
| 修正特有的大数组 | 独立写入`cal/`下的修正文件 | 保持L1/L2不可变，隔离写入 |
| 后台任务返回值 | 数量、耗时、文件路径、版本等小摘要 | 避免整份节点数据再次进入任务JSON |

建议后续顺序：

1. 用新增日志分清重读源文件、对象整理、写库、索引压缩各阶段，不能把总等待全算成MySQL写入。
2. 检查各调用方，去掉重复的大任务返回体，仅保留统计和文件引用。
3. 字段、坐标系与编号映射一致时复用L1 H5。现有L1不完整的材料密度、约束或特殊属性不能推导或丢弃，需设计下一次首次导入时补充提取。
4. 给现有SQL/H5/NPZ和后续统一H5建立兼容读取入口，不做全库迁移。节点使用`(instance_name, label)`匹配，不能假设裸编号全局唯一。
5. 文件坚持单写者，临时写入、校验后原子发布，再登记版本；定义源文件变化、重传和删除的失效规则。
6. 验证节点数、阶次、坐标系、编号映射、有限值、抽样数值及下游匹配/模态相关性后再切换。按访问方式测试H5分块和压缩，不承诺换格式必然提速。

本次不迁移数据库，不重建200万模型，不自动重新导入其修正数据。
