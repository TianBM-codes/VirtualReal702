# 商业软件参数选择与灵敏度分析说明

## 目标

本文档描述 `/optimization/parameter/create` 以及后续灵敏度求解、模型修正链路中，Abaqus 与 Nastran 参数是如何被选择、唯一化、落库并参与后续计算的。

这里说的“参数选择逻辑”不是单指接口入参校验，而是完整链路：

1. 从模型中提取可选参数候选
2. 用户或前端选择候选集合
3. 系统补全参数定位信息
4. 创建正式优化参数
5. 参数进入灵敏度求解 / 模型修正流程
6. 结果再映射回参数目标

## 一、统一抽象

虽然 Abaqus 和 Nastran 的模型组织方式不同，但在参数选择这件事上，可以统一成下面三层概念。

### 1. 参数身份

参数“是谁”，由以下字段表达：

- `parameter_group_name`
- `parameter_name`

其中：

- `parameter_group_name` 表示一组参数的业务分组
- `parameter_name` 表示最终落库的唯一参数名

数据库中真正稳定的参数身份是 `parameter_name`。

### 2. 参数作用目标

参数“控制哪里”，由以下字段共同表达：

- `quantity_code`
- `set_name`
- `set_type`
- `set_scope`
- `instance_name`
- `part_name`
- `element_label`
- `extra_json.element_labels`
- `extra_json.target_keys`

这些字段不是每次都要用户全部显式传入，但在系统内部，最终必须补全成足以唯一定位目标的完整形式。

### 3. 参数求解属性

参数“如何参与后续计算”，由以下字段表达：

- `selection_mode`
- `current_value`
- `lower`
- `upper`
- `scatter`
- `usage_scope`

这些字段用于：

- 灵敏度求解
- 贝叶斯修正
- 结果归一化
- 参数筛选与分用途管理

## 二、参数选择的总流程

### 1. 导入阶段生成候选目录

无论 Abaqus 还是 Nastran，导入模型后都不会直接创建正式优化参数，而是先生成“候选能力目录”：

- `t_mt_py_fem_supported_quantity`
- `t_mt_py_fem_quantity_set_capability`

其中：

- `supported_quantity` 描述支持哪些物理量，例如 `E / T / RHO`
- `quantity_set_capability` 描述这些物理量在哪些集合上可用，以及集合支持 `GLOBAL` 还是 `LOCAL`

这是参数选择的上游来源。

### 2. 前端/调用方选择候选

调用方通常从候选目录里选中某个量和某个集合，例如：

- `quantity_code = E`
- `set_name = SET_SHELL`

或者在 Nastran 中：

- `quantity_code = E`
- `set_name = PROPERTY_12`

这一步只是在表达“我要针对哪个候选创建参数”，还不是最终完整参数定义。

### 3. 系统解析并补全目标

创建参数时，系统会根据候选目录进一步解析：

- `set_type`
- `set_scope`
- `instance_name`
- `part_name`
- `element_labels`
- `target_keys`
- `current_value`

如果 `quantity_code + set_name` 已经足够唯一，则自动补全。
如果不够唯一，则要求继续补充消歧字段。

### 4. 正式创建参数

完成目标解析后，系统按 `GLOBAL` 或 `LOCAL` 创建正式参数：

- `GLOBAL`：一个集合创建一条正式参数
- `LOCAL`：一个集合中的每个单元扩展为一条正式参数

正式参数落入：

- `t_mt_py_fem_selected_parameter`

### 5. 后续求解使用正式参数

后续灵敏度求解、模型修正、结果回填，不再依赖“用户原始输入”，而是依赖正式参数表中的完整定位信息。

也就是说，真正参与后续计算的是“补全后的参数”，不是“简写输入”。

## 三、Abaqus 参数选择逻辑

## 3.1 目标类型

如果当前业务只考虑单元参数，那么对 Abaqus 来说：

- `set_type` 应固定为 `ELSET`

因为参数最终控制的是一组单元。

注意：

- `ELSET` 描述的是“参数作用对象类型”
- `PART / ASSEMBLY` 描述的是“该 ELSET 定义在哪个命名空间”

它们不是互斥关系，而是两个维度。

## 3.2 PART 与 ASSEMBLY 的区别

### `set_scope = PART`

表示该 `ELSET` 定义在 `Part` 内。

这类参数的语义是：

- 参数作用于某个 Part 定义上的单元集合
- 如果这个 Part 在装配中被实例化多次，那么这个 Part 级参数会影响所有引用该 Part 的实例

因此：

- `PART` 级参数不是“某一个实例的参数”
- 它是“Part 模板上的参数”

典型定位字段：

- `set_type = ELSET`
- `set_scope = PART`
- `part_name`
- `set_name`

### `set_scope = ASSEMBLY`

表示该 `ELSET` 定义在 `Assembly` 层，通常关联到某个具体实例。

这类参数的语义是：

- 参数只作用于某个具体 `instance` 上的一组单元

因此：

- `ASSEMBLY` 级参数是“实例级参数”

典型定位字段：

- `set_type = ELSET`
- `set_scope = ASSEMBLY`
- `instance_name`
- `set_name`

`part_name` 在这种场景下通常是辅助信息，不是主定位键。

## 3.3 Abaqus 中为什么会混淆

容易混淆的原因是：

- INP 中很多属性也是“按 ELSET 指定”的
- 于是看起来好像所有参数都只是“选一个 ELSET”

但实际上：

- “参数作用目标是 ELSET” 只说明目标类型
- “这个 ELSET 在 PART 还是 ASSEMBLY” 才决定参数是 Part 级还是 Instance 级

所以完整理解应该是：

- `ELSET + PART` = Part 级单元参数
- `ELSET + ASSEMBLY` = Instance 级单元参数

两者都叫“按 ELSET 建参数”，但语义不同。

## 3.4 Abaqus 创建参数时的推荐规则

### 最简输入

如果候选唯一，可只传：

- `quantity_code`
- `set_name`

然后让系统自动补全。

### 稳定输入

如果存在歧义，建议显式补充：

- `set_type = ELSET`
- `set_scope`
- `part_name` 或 `instance_name`

推荐组合：

- `PART` 参数：`quantity_code + set_name + set_scope=PART + part_name`
- `ASSEMBLY` 参数：`quantity_code + set_name + set_scope=ASSEMBLY + instance_name`

## 3.5 Abaqus 参数如何进入后续灵敏度链路

对于 Abaqus DSA：

1. 正式参数表保存参数定义
2. 生成 DSA `inp`
3. `DESIGN VARIABLES` 顺序决定 `T1 / T2 / ...`
4. 求解输出 `d_U_T1`、`d_U_T2` 等字段
5. 再根据正式参数表把结果映射回参数目标

因此 Abaqus 参数不仅要能“被选中”，还要能：

- 稳定落到某个 ELSET
- 稳定进入设计变量顺序
- 稳定反查回目标单元

## 四、Nastran 参数选择逻辑

## 4.1 Nastran 与 Abaqus 的根本区别

Nastran 没有 Abaqus 那种：

- `Part`
- `Instance`
- `Assembly`

的层级建模语义。

Nastran 更接近全局卡片模型：

- 材料定义是全局的
- 属性定义是全局的
- 单元直接引用属性和材料

因此 Nastran 的参数选择逻辑不应强行套 Abaqus 的 `part_name / instance_name` 模型。

## 4.2 Nastran 中参数的常见目标

当前导入逻辑中，Nastran 候选参数通常来自两类集合：

- `PROPERTY_xxx`
- `MAT1_xxx`

也就是：

- 以 property 为目标的一组单元
- 以 material 为目标的一组单元

典型字段是：

- `quantity_code`
- `set_name`
- `set_type = PROPERTY / MATERIAL`
- `extra_json.element_labels`

## 4.3 Nastran 参数的唯一化

由于没有 `PART / ASSEMBLY` 层级，Nastran 参数的唯一化重点通常是：

- `quantity_code`
- `set_name`
- `set_type`

必要时再依赖：

- `element_labels`

因此：

- 对 Nastran 来说，`part_name` 通常不是核心语义
- 真正决定参数落点的是它控制的那组单元

## 4.4 Nastran 创建参数时的推荐规则

### 最简输入

如果候选唯一，可只传：

- `quantity_code`
- `set_name`

### 稳定输入

更推荐显式补：

- `set_type`

例如：

- `quantity_code = E`
- `set_name = PROPERTY_12`
- `set_type = PROPERTY`

或者：

- `quantity_code = E`
- `set_name = MAT1_3`
- `set_type = MATERIAL`

## 五、GLOBAL 与 LOCAL 的区别

这部分对于 Abaqus 和 Nastran 都成立。

### `selection_mode = GLOBAL`

表示：

- 整个集合对应一个参数

例如：

- 整个 `SET_SHELL` 厚度一起变
- 整个 `PROPERTY_12` 弹性模量一起变

### `selection_mode = LOCAL`

表示：

- 集合中每个单元拆成一个参数

系统会把一个集合展开成多条正式参数，每条参数对应一个单元。

这是后续细粒度修正和局部敏感性分析的基础。

## 六、手工单元选择与目录选择

参数创建有两类入口：

### 1. 按已有集合创建

输入核心是：

- `quantity_code`
- `set_name`

再由系统从 capability 目录解析完整目标。

### 2. 按手工单元创建

输入核心是：

- `quantity_code`
- `element_labels`

这种场景下没有现成集合，系统会创建虚拟集合名，并直接以用户选中的单元集作为参数目标。

## 七、参数重叠约束

为了保证后续灵敏度和模型修正语义稳定，同一 `quantity_code` 下不允许目标范围重叠。

无论是：

- Abaqus 的 `ELSET`
- Nastran 的 `PROPERTY/MATERIAL`
- 手工元素集

最终都会被归约成一组单元标签来检查是否重叠。

这条约束的本质是：

- 同一个物理量不能由两条正式参数同时控制同一单元

否则后续求解和结果回映射会失去确定性。

## 八、响应选择逻辑

本文档中的“响应”主要指用于 Abaqus DSA 静力灵敏度分析的设计响应，也就是后续会进入 `*DESIGN RESPONSE` 配置并参与灵敏度输出的响应定义。

与参数类似，响应设置也不是简单的接口入参问题，而是一条完整链路：

1. 选择响应区域
2. 选择响应变量
3. 确定作用步和输出频次
4. 创建正式响应目录记录
5. 在生成 DSA `inp` 时写入真实响应定义
6. 在后处理时用这些响应定义解释灵敏度场

### 8.1 响应的统一抽象

一个正式响应主要由以下几组字段表达：

- 区域字段：
  - `region_type`
  - `set_name`
  - `set_scope`
  - `instance_name`
  - `part_name`
  - `node_labels`
  - `element_labels`
- 变量字段：
  - `variables`
- 求解字段：
  - `step_name`
  - `frequency`
- 标识字段：
  - `response_no`
  - `request_no`
  - `response_name`

其中最关键的是：

- 响应取值取哪里
- 响应取什么变量
- 它属于哪个分析步

### 8.2 响应创建的两种入口

和参数类似，响应创建也有两类入口。

#### 1. 按已有集合创建

调用方传：

- `region_type`
- `set_name`
- `variables`

这种模式表示：

- 响应目标已经由模型中的 `NSET` 或 `ELSET` 定义好
- 后端只需要记录这条响应配置

#### 2. 按手工标签创建

调用方传：

- `region_type`
- `node_labels` 或 `element_labels`
- `variables`

这种模式表示：

- 没有直接复用现成集合
- 系统会为这组标签自动生成一个逻辑响应集合名
- 后续在生成 DSA `inp` 时再把它写成真实 `NSET/ELSET`

### 8.3 `region_type` 的语义

- `NODE`：响应定义在节点上
- `ELEMENT`：响应定义在单元上

约束关系是：

- `region_type=NODE` 时，只能使用 `set_name` 或 `node_labels`
- `region_type=ELEMENT` 时，只能使用 `set_name` 或 `element_labels`
- `set_name` 和标签列表必须二选一

### 8.4 `variables` 的语义

`variables` 表示在该响应区域上关心什么场量，例如：

- `["U2"]`：节点第二方向位移
- `["S11"]`：单元应力分量

对 Abaqus DSA 来说，响应变量最终会转换成生成器可接受的响应定义。如果传入的是方向型变量，系统后续可能会映射成 Abaqus 更基础的变量表达，这一点属于生成器兼容处理，不改变“你选择了哪个物理响应”的业务语义。

### 8.5 `step_name` 的语义

`step_name` 用于指定该响应属于哪个分析步。

在静力灵敏度场景里，这个字段很重要，因为：

- 同一个模型可能有多个分析步
- 同一个节点或单元在不同步里可能有不同响应值

因此，真正锁定一条响应时，通常不能只看“区域 + 变量”，还要看它属于哪个 `step_name`。

### 8.6 `frequency` 的语义

这里的 `frequency` 不是模态频率 Hz，也不是节点号或单元号。

它表示的是：

- 该设计响应在求解/输出层面的请求频次
- 对应 Abaqus `*DESIGN RESPONSE` 中的 `FREQUENCY` 概念

在当前静力 DSA 场景里：

- 默认值是 `1`
- 最常见也最推荐直接使用 `1`

因此可以这样理解：

- `frequency` 是响应配置字段
- 它不是用来唯一锁定响应位置的主键字段

### 8.7 Abaqus 节点响应的唯一化逻辑

对于节点位移这类响应，真正的定位核心是节点身份，而不是集合身份。

如果调用方已经给出：

- `region_type = NODE`
- `instance_name`
- `node_label`
- `step_name`
- `variable`

那么从业务语义上说，这条响应通常已经可以被稳定锁定。

以位移响应为例，核心定位可理解为：

- `step_name + instance_name + node_label + variable`

在这种场景下：

- `set_scope` 通常不是锁定节点所必需的
- `part_name` 通常是辅助信息，不是主定位键

也就是说，对于手工节点响应：

- `instance_name + node_labels` 比 `set_scope` 更关键

### 8.8 为什么响应里还保留 `set_scope / part_name / instance_name`

因为响应目录采用的是与参数目录相近的统一建模方式，需要同时兼容：

- set-based 响应
- 手工标签响应

所以这几个字段保留的意义是：

- 对已有 `set_name` 的响应，描述集合所在命名空间
- 对手工标签响应，保留上下文，供后续生成器和结果解释使用

可以这样区分：

- `set_name` 模式：`set_scope` 有意义，用于区分集合命名空间
- `node_labels + instance_name` 模式：`set_scope` 对节点锁定本身通常是冗余的

### 8.9 Abaqus 单元响应的唯一化逻辑

对于单元响应，逻辑和参数更接近。

如果是已有集合模式：

- 通常通过 `set_name + set_scope + part_name/instance_name + variable + step_name` 来理解

如果是手工标签模式：

- 通常通过 `instance_name + element_labels + variable + step_name` 来理解

因此，单元响应依然有明显的“命名空间”问题，而节点响应更偏“实体定位”问题。

### 8.10 Nastran 响应的注意事项

Nastran 没有 Abaqus 的 `Part / Instance / Assembly` 层级语义，因此在 Nastran 场景下，不应强行把响应定位建立在 `set_scope / part_name / instance_name` 上。

更自然的理解是：

- 响应落在全局节点或全局单元上
- 或者落在某个全局 property/material 所覆盖的区域上

因此 Nastran 响应的定位语义通常更接近：

- `node_id + variable + case`
- `element_id + variable + case`

而不是 Abaqus 风格的实例层级。

### 8.11 响应如何进入灵敏度链路

正式响应创建完成后，会保存到设计响应目录中。后续生成 DSA `inp` 时，系统会读取这些正式响应记录，转换成生成器需要的响应配置。

这意味着：

- 后续灵敏度求解依赖的是正式响应目录
- 不是依赖调用方最初那次接口请求本身

所以和参数一样，真正参与求解的是“落库后的正式响应定义”。

### 8.12 响应设置的实务建议

对 Abaqus 静力位移响应，推荐优先按下面的方式理解和设置：

- 节点响应：
  - 优先关心 `instance_name + node_label + variable + step_name`
  - `set_scope` 不是主定位字段
  - `part_name` 是辅助字段
- 单元响应：
  - 如果按集合建响应，`set_scope` 有意义
  - 如果按手工单元建响应，优先关心 `instance_name + element_labels + variable + step_name`

对 `frequency`：

- 一般固定用 `1`
- 不要把它理解成模态频率
- 不要把它当作响应唯一化字段

## 九、参数创建自动补全规则

### 8.1 简写输入

在“按已有集合创建参数”的场景里，调用方最常见的输入是：

- `quantity_code`
- `set_name`

这两个字段表达的是“我要对哪个物理量、哪个集合创建参数”，但它们通常不是最终写入正式参数目录的完整定位信息。

因此，系统应将 `quantity_code + set_name` 视为“待解析的集合引用”，而不是已经完整定位的参数目标。

### 8.2 自动补全来源

程序应查询 `t_mt_py_fem_quantity_set_capability`，按以下顺序解析目标集合：

1. 先按 `pid + quantity_code + set_name` 查找候选集合
2. 如果请求中额外提供了 `set_type / set_scope / instance_name / part_name`，则继续用于缩小候选范围
3. 如果最终只命中一条 capability 记录，则自动补全：
   - `set_type`
   - `set_scope`
   - `instance_name`
   - `part_name`
   - capability 中保存的 `element_labels / target_keys / current_value`

### 8.3 唯一命中时的行为

如果 `quantity_code + set_name` 只命中一条 capability 记录，则视为可自动补全成功，后续参数创建流程使用补全后的完整信息继续执行。

这条规则适用于：

- Abaqus 的 `ELSET`
- Nastran 导入后生成的 `PROPERTY_xxx` / `MAT1_xxx` 等集合能力

### 8.4 多条命中时的行为

如果 `quantity_code + set_name` 命中多条 capability 记录，则说明 `set_name` 在当前工程内不唯一，程序不能自行猜测目标集合，必须报歧义错误，并要求调用方继续补充：

- `set_type`
- `set_scope`
- `instance_name`
- `part_name`

实际需要补哪几个字段，以能够把候选集合收敛到唯一一条为准。

## 十、接口层结论

### Abaqus

如果只考虑单元参数：

- `set_type` 应理解为固定 `ELSET`
- `set_scope` 用于区分 `PART` 和 `ASSEMBLY`

推荐规则：

- `PART` 参数：`quantity_code + set_name + part_name`
- `ASSEMBLY` 参数：`quantity_code + set_name + instance_name`
- 如果同名集合唯一，则允许只传 `quantity_code + set_name`

### Nastran

不需要引入 Abaqus 风格的 `Part / Instance` 层级。

推荐规则：

- `quantity_code + set_name`
- 必要时补 `set_type`

### 统一结论

`quantity_code + set_name` 可以作为创建参数时的简写输入，但它不是参数最终的完整身份。

系统必须把它解析成完整定位信息，最终落库为正式参数，后续灵敏度和模型修正流程只依赖这份补全后的正式参数定义。

对于响应也一样：

- 调用方可以用较简洁的方式声明响应
- 但后续生成灵敏度 `inp` 和解释结果时，依赖的是正式响应目录里的完整定义

## 十一、与实现的对应关系

当前实现中，这套逻辑主要落在：

- `import_inp_catalog`：导入目录与候选能力生成
- `_extract_quantity_set_capabilities`：提取可选参数集合能力
- `get_inp_parameter_options`：返回可选参数目录
- `create_optimization_parameter`：把候选集合创建成正式参数
- `create_design_response_catalog_entry`：把集合或手工标签创建成正式响应
- `t_mt_py_fem_selected_parameter`：保存正式参数
- `t_mt_py_fem_static_sensitivity_response_catalog`：保存正式响应
