# 接口补充（2026-05-13）

这份补充文档对应三项改动：

1. 数据库连接池改为在 `app.py` 启动阶段预热  
2. 模态相关性 `MAC` 增加“矩阵/图表”和“表格”两种返回  
3. `SOL200` 灵敏度后处理接口不再要求前端必须传 `metadata_json`

## 1. 数据库连接池启动预热

### 目的

以前连接池是“第一次有人调接口时才创建”。  
这样会导致服务刚重启后，前端第一次调用像：

- `/get/sensor_position`
- `/get/sensor_relative_error`

这种接口时，看起来会特别卡。

现在改成：

- 服务启动时就创建连接池
- 并主动预热一次数据库连接
- 同时提前做一次表结构检查

这样做的好处是：

- 首次接口延迟更稳定
- 数据库配置有问题时，服务启动阶段就能直接暴露

## 2. MAC 返回接口

### 2.1 `POST /correlation/modal`

功能说明：

- 读取已经计算并落库的 `MAC` 结果
- 返回适合热力图/矩阵图表展示的数据结构
- 返回风格对齐灵敏度矩阵接口

请求示例：

```json
{
  "project_id": 1002
}
```

返回 `data` 示例：

```json
{
  "project_id": 1002,
  "row_mode_order": ["7", "8"],
  "column_mode_order": ["1", "2"],
  "data": {
    "rows": ["7", "8"],
    "column": ["1", "2"],
    "data": [
      [0, 0, 0.973],
      [0, 1, 0.081],
      [1, 0, 0.102],
      [1, 1, 0.956]
    ]
  },
  "summary": {
    "fem_mode_count": 2,
    "test_mode_count": 2,
    "point_count": 4
  }
}
```

字段解释：

- `rows`：FEM 模态阶次，作为矩阵行
- `column`：试验模态阶次，作为矩阵列
- `data`：`[row_index, col_index, value]` 三元组，适合前端热力图直接消费

### 2.2 `POST /correlation/modal/matrix`

功能说明：

- 与 `/correlation/modal` 含义一致
- 这是单独保留的矩阵接口，便于前端显式按“热力图数据源”使用

请求示例：

```json
{
  "project_id": 1002
}
```

### 2.3 `POST /correlation/modal/table`

功能说明：

- 读取已经计算并落库的 `MAC` 结果
- 返回适合表格显示的数据结构
- 返回风格对齐灵敏度表格接口

请求示例：

```json
{
  "project_id": 1002
}
```

返回 `data` 示例：

```json
{
  "project_id": 1002,
  "row_mode_order": ["7", "8"],
  "column_mode_order": ["1", "2"],
  "rows": ["7", "8"],
  "column": ["1", "2"],
  "data": [
    {
      "1": 0.973,
      "2": 0.081
    },
    {
      "1": 0.102,
      "2": 0.956
    }
  ],
  "summary": {
    "fem_mode_count": 2,
    "test_mode_count": 2,
    "point_count": 4
  }
}
```

字段解释：

- `rows`：FEM 模态阶次
- `column`：试验模态阶次
- `data`：每一行是一个 FEM 模态，对应一个“列名 -> MAC值”的字典

### 2.4 `POST /correlation/modal/msf/table`

功能说明：

- 读取已经计算并落库的 `MSF` 结果
- 返回适合表格显示的数据结构
- 返回风格与 `POST /correlation/modal/table` 保持一致，只是数值由 `MAC` 改为 `MSF`

请求示例：

```json
{
  "project_id": 1002
}
```

返回 `data` 示例：

```json
{
  "project_id": 1002,
  "row_mode_order": ["7", "8"],
  "column_mode_order": ["1", "2"],
  "rows": ["7", "8"],
  "column": ["1", "2"],
  "data": [
    {
      "1": 2.25,
      "2": 0.5
    },
    {
      "1": 1.75,
      "2": 1.0
    }
  ],
  "summary": {
    "fem_mode_count": 2,
    "test_mode_count": 2,
    "point_count": 4
  }
}
```

字段解释：

- `rows`：FEM 模态阶次
- `column`：试验模态阶次
- `data`：每一行是一个 FEM 模态，对应一个“列名 -> MSF值”的字典

## 3. `metadata_json` 现在不是前端必填

影响接口：

- `POST /import/op2/sensitivity/preview`
- `POST /import/op2/sensitivity/store`
- `POST /export/op2/sensitivity/vtu`

### 现在的规则

如果你传了：

- `project_id`
- `batch_no`

那么后端会优先去 MySQL 里找这一次 `SOL200` 运行时已经保存下来的过程元数据，包括：

- 响应行定义
- 参数列定义
- `bdf_path`
- `matrix_path`
- `op2_path`

也就是说：

- `metadata_json` 现在是**可选兜底参数**
- 不是前端主流程里的必填项

### 为什么这样更合理

因为 `metadata_json` 本质上只是一个“过程说明书文件”。  
如果后端已经把这些说明书内容存进数据库了，那么前端每次再传一遍文件路径，其实既麻烦也不稳。

所以现在推荐你前端优先这样用：

1. `SOL200 run` 时传 `project_id + batch_no`
2. 后面 `preview / store / vtu export` 继续传同样的 `project_id + batch_no`
3. 不再把 `metadata_json` 当成必填项
