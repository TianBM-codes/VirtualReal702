# 统一参数响应目录与灵敏度修正方案

## 1. 目标

本方案解决两个实际问题：

1. 灵敏度计算和真正模型修正不是同一个阶段，参数集合可能不同。
2. 静力响应、动力响应、后续模态 `MAC` 响应，希望尽量统一管理，而不是各走各的表。

整体思路是：

- `t_mt_py_fem_modal_correlation` 继续只做模态匹配候选池。
- `t_mt_py_fem_selected_parameter` 升级为统一正式参数目录。
- `t_mt_py_fem_response_catalog` 升级为统一正式响应目录。
- 不同求解流程只从统一目录里过滤自己需要的参数和响应。

## 2. 参数目录

### 2.1 表定位

`t_mt_py_fem_selected_parameter` 继续作为正式参数表，但增加“用途范围”语义。

### 2.2 新增语义

新增字段：

- `usage_scope`

推荐值：

- `["SENSITIVITY"]`
- `["UPDATE"]`
- `["SENSITIVITY", "UPDATE"]`

含义：

- `SENSITIVITY`：该参数参与灵敏度计算。
- `UPDATE`：该参数参与真正模型修正。

### 2.3 业务意义

这样就能支持下面这条流程：

1. 先创建一批候选参数。
2. 用这些参数做灵敏度计算。
3. 根据灵敏度结果，只把高灵敏度参数标记为 `UPDATE`。
4. 后续模型修正只读取带 `UPDATE` 的参数。

## 3. 响应目录

### 3.1 表定位

`t_mt_py_fem_response_catalog` 升级为统一正式响应目录。

它保存的是“当前项目正式选中的响应”，而不是候选结果。

### 3.2 新增字段

- `enabled`
- `selection_source`
- `solver_scope`
- `updated_at`

字段含义：

- `enabled`：该响应是否启用。
- `selection_source`：该响应是手工创建、手工选模态对，还是自动从模态匹配结果生成。
- `solver_scope`：该响应准备给哪个流程使用。
- `updated_at`：最后修改时间。

### 3.3 响应类型

当前建议先统一支持：

- `STATIC_DISPLACEMENT`
- `STATIC_STRESS`
- `STATIC_STRAIN`
- `MODAL_FREQUENCY`
- `MODAL_MAC`

## 4. 模态匹配候选池

`t_mt_py_fem_modal_correlation` 的定位不变：

- 它只保存候选 `(test_mode_no, fem_mode_no)` 配对及其相关性指标。
- 它不是正式响应表。
- 用户真正选中的模态对，要单独写入 `t_mt_py_fem_response_catalog`。

## 5. 模态响应唯一性

模态正式响应按下面的业务唯一性管理：

- `(pid, response_type, test_mode_no, fem_mode_no)`

这样同一对模态可以同时存在：

- 一条 `MODAL_FREQUENCY`
- 一条 `MODAL_MAC`

但同一种响应类型不重复。

## 6. 推荐接口

### 6.1 参数接口

- `POST /optimization/parameter/create`
  - 创建候选参数
- `POST /optimization/parameter`
  - 查询正式参数目录
- `POST /optimization/parameter/usage/update`
  - 批量更新参数用途范围
- `POST /optimization/parameter/select_for_update`
  - 把一批参数标记为进入模型修正
- `POST /optimization/parameter/remove_from_update`
  - 把一批参数从模型修正集合中移除

### 6.2 响应接口

- `POST /optimization/response/create`
  - 创建静力正式响应
- `POST /optimization/response/catalog`
  - 查询统一正式响应目录
- `POST /optimization/response/clear`
  - 清空正式响应目录
- `POST /optimization/response/modal_match/select`
  - 保存用户选择的模态匹配对
- `POST /optimization/response/modal_frequency/create_from_match`
  - 自动从模态匹配结果批量生成推荐频率响应

### 6.3 候选接口

- `POST /correlation/modal/compute`
  - 计算模态相关性候选池
- `POST /correlation/modal/match/preview`
  - 预览候选匹配对
- `POST /correlation/modal/match`
  - 生成当前条件下的自动一对一匹配结果

## 7. 各流程如何消费

### 7.1 DSA / 灵敏度计算

读取：

- 参数：`usage_scope` 包含 `SENSITIVITY`
- 响应：`solver_scope` 包含 `DSA`

### 7.2 SOL200

读取：

- 参数：
  - 灵敏度阶段读 `SENSITIVITY`
  - 修正阶段读 `UPDATE`
- 响应：
  - `solver_scope` 包含 `SOL200`
  - `response_type` 属于 `MODAL_FREQUENCY` / `MODAL_MAC`

### 7.3 Bayesian 模态修正

读取：

- 参数：`usage_scope` 包含 `UPDATE`
- 响应：
  - `solver_scope` 包含 `BAYESIAN`
  - `response_type` 属于 `MODAL_FREQUENCY` / `MODAL_MAC`

## 8. 推荐落地顺序

建议按下面顺序逐步改，不要一下子推翻旧链：

1. 给参数表增加 `usage_scope`
2. 给响应表增加 `enabled / selection_source / solver_scope / updated_at`
3. 新增参数用途更新接口
4. 新增模态匹配对手工选择接口
5. 让灵敏度 / SOL200 读取时开始按用途和范围过滤
6. 后续再逐步把旧接口迁移到统一目录语义

## 9. 第一批实现边界

为了不打断现有使用方式，第一批程序修改建议采用“增量接入”：

- 保留旧接口继续可用
- 新接口先补齐
- 新字段先开始落库和回传
- 下游流程先在参数和响应过滤点接入新语义

这样开发者本地 `git pull` 后可以逐步切换，不需要一次性重做全部前端逻辑。
