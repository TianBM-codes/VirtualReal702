# 灵敏度接口临时线程池方案

## 背景

`/sensitivity/abaqus/run_and_store` 这条链路当前同时承担了以下长流程：

1. 运行 Abaqus 求解
2. 调 `tools/run_l1.py` 解析 ODB 并重建 workspace
3. 读取灵敏度矩阵
4. 存库
5. 可选写回 `/api/odb/{odb_id}/results/external-field`

这导致两个短期问题：

1. `write_cloud_result=true` 时，如果 body 中包含 `NaN/Inf`，会在 HTTP 客户端 JSON 序列化阶段报 `Out of range float values are not JSON compliant`
2. 接口虽然是 `async def`，但内部调用的是同步长任务，worker 会被长时间占用

## 本次临时方案

### 1. cloud body 先做 JSON 合法性修复

处理点：

1. external-field body 中的 component 占位值不再使用 `NaN`，改为 `0.0`
2. 灵敏度矩阵写回 cloud 前，显式校验矩阵值必须为有限浮点
3. DSA 归一化后如果出现非有限值，提前抛出可读错误
4. `_post_json` 对 JSON 非法 body 增加更明确的错误提示

这样能避免原来的 requests JSON 序列化错误，并把真实数据异常暴露在更靠前的位置。

### 2. 长流程临时丢到线程池后台执行

新增临时线程池任务注册表，用于把以下接口改成“可后台提交”：

1. `/sensitivity/abaqus/calculate_and_store`
2. `/sensitivity/abaqus/run_and_store`
3. `/sensitivity/abaqus/generate_run_and_store`

请求体新增：

```json
{
  "async_submit": true
}
```

当 `async_submit=true` 时：

1. 接口立即返回 `task_id`
2. 实际长流程在线程池中继续执行
3. 可通过 `GET /sensitivity/tasks/{task_id}` 查询状态

任务状态当前为内存态：

1. `submitted`
2. `running`
3. `succeeded`
4. `failed`

## 当前限制

这是一期临时方案，明确有这些限制：

1. 任务状态存在当前进程内存里，服务重启后会丢失
2. 多进程部署下，各 worker 之间不共享这份任务状态
3. 线程池只解决“请求不阻塞当前 worker 返回”，不等于完整任务平台
4. 结果查询仍建议优先使用现有存库查询接口：
   - `/sensitivity/stored/table`
   - `/sensitivity/stored/matrix`

## 二期建议

二期建议切到正式任务体系，而不是继续扩线程池：

1. 增加 sensitivity task 表，持久化状态、参数、错误和结果摘要
2. 将灵敏度长流程接入独立 runner，而不是挂在线程池内存任务上
3. 增加任务取消、重试、日志查询、进度上报
4. 将“求解、ODB 解析、矩阵存库、云图写回”拆成明确阶段
5. 对接现有 `job_runner` / `runner_thread` 的模式，统一后台执行框架
