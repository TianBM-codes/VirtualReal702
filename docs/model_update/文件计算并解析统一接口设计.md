# 文件计算并解析统一接口设计

## 1. 文档目的

本文档用于设计一个新的统一接口，支持前端传入一个模型文件，由后端自动：

1. 识别文件类型是 `inp` 还是 `bdf`
2. 根据文件类型调用对应求解器
   - `inp` -> Abaqus
   - `bdf` -> Nastran
3. 在求解完成后，自动调用现有“项目解析 / 结果解析”接口
4. 最终把结果接入当前项目主链路，而不是额外造一套独立流程

这份设计稿的重点不是“怎么跑一个命令”，而是回答下面几个更关键的问题：

1. 新接口应该挂在哪一层
2. 应该复用哪些现有解析接口
3. `inp` 和 `bdf` 分别怎么接到现有架构里
4. 状态流转、前后端调用顺序、返回值应该怎么设计

## 2. 先说结论

这个新接口本质上不是“解析接口”，而是一个“编排接口”。

意思是：  
它不是只负责读文件，而是要把好几步串起来：

1. 建项目或找到项目
2. 跑求解器
3. 拿到结果文件
4. 再调用现有解析接口把结果挂到项目里

所以它更适合放在现有求解器编排层：

- 路由层：`webapi/routers/solver.py`
- 服务层：`services/model_update/analysis/solver_service.py`

而不建议直接塞进：

- `src/l3/api/routes/projects.py`

因为 `projects.py` 这层的职责是“项目解析”和“结果组解析”，不是“调外部求解器”。

## 3. 现有可复用接口分析

### 3.1 项目创建 / 几何解析接口

位置：

- [src/l3/api/routes/projects.py](/D:/WorkSpace/OtherProjects/VirtualReal702/src/l3/api/routes/projects.py)

核心接口：

- `POST /api/projects`

作用：

- 创建项目
- 根据 `source_type` 解析几何主文件

当前已经支持：

- `inp`
- `odb`
- `bdf`
- `op2`

这里最重要的点是：

- `inp` 可以作为项目的几何源
- `bdf` 也可以作为项目的几何源

也就是说，新的统一接口没必要自己重新做“几何解析”，直接复用这个接口就行。

### 3.2 结果组追加接口

位置同上。

核心接口：

- `POST /api/projects/{project_id}/results`

作用：

- 给一个已经有几何的项目，追加一个结果组

这个接口正好对应求解后的第二段动作：

- Abaqus 求解完得到 `.odb`
- Nastran 求解完得到 `.op2`
- 然后把这个结果文件作为 `source_path` 传进去

这就是现有系统里最合适的“解析结果入口”。

### 3.3 真正执行解析的后台作业

位置：

- [src/job_runner.py](/D:/WorkSpace/OtherProjects/VirtualReal702/src/job_runner.py)

现有分支已经比较完整：

- `_run_odb_project()`
- `_run_bdf_project()`
- `_run_op2_project()`
- `_run_result_group()`
- `_run_op2_result_group()`

大白话解释一下：

- 项目几何怎么解析，`job_runner.py` 已经会做
- 结果组怎么解析，`job_runner.py` 也已经会做
- 新接口真正缺的不是解析能力，而是“把求解器和解析接口接起来”

### 3.4 当前已有的“求解后上传解析”能力

位置：

- [services/model_update/analysis/solver_service.py](/D:/WorkSpace/OtherProjects/VirtualReal702/services/model_update/analysis/solver_service.py)

现有能力里，Abaqus 这一条已经有接近成型的例子：

- `run_abaqus_inp_and_upload_project_result()`

它已经做了两件事：

1. 运行 Abaqus
2. 调用 `POST /api/projects/{project_id}/results` 把 `.odb` 结果挂到项目里

这说明新的统一接口并不是从零开始，Abaqus 这半边可以直接沿着现有实现扩展。

## 4. 为什么不要新开一套“文件计算解析专用链路”

如果新接口直接自己做一套：

- 上传文件
- 跑求解器
- 自己落库
- 自己维护状态

短期看好像快，长期会有几个问题。

### 4.1 会出现两套项目状态系统

现在项目主链路已经有：

- `projects`
- `result_groups`
- `geom_status`
- `result_group status`
- `job_runner`

如果新接口再做一套，后面前端就要区分：

- 这是“项目解析出来的结果”
- 还是“求解接口自己存的结果”

这会让前后端都越来越乱。

### 4.2 Abaqus 和 Nastran 会被做成两种风格

当前项目的好处是，虽然输入格式不同，但最终都往同一套项目 / 结果组结构收敛。

如果新接口直接绕开项目接口：

- `inp` 可能走一套逻辑
- `bdf` 又走另一套逻辑

最后前端看起来就不像一个系统了。

### 4.3 后续功能不好复用

后续如果要接：

- 日志查询
- 结果组重命名
- 项目克隆
- 几何重跑
- result_group 查询

复用现有项目主链路会简单很多。

## 5. 推荐的统一设计原则

推荐统一遵守下面一句话：

**`inp / bdf` 负责项目几何，`odb / op2` 负责结果挂载。**

拆开解释：

### 5.1 `inp`

`inp` 是 Abaqus 输入文件，最适合拿来创建项目几何。

流程应该是：

1. `inp` 创建项目
2. Abaqus 计算得到 `odb`
3. `odb` 作为结果组追加到这个项目

### 5.2 `bdf`

`bdf` 是 Nastran 输入文件，最适合拿来创建项目几何。

流程应该是：

1. `bdf` 创建项目
2. Nastran 计算得到 `op2`
3. `op2` 作为结果组追加到这个项目

### 5.3 为什么这么拆

因为这样最符合当前架构：

- 项目层负责“模型长什么样”
- 结果组层负责“这个模型跑出来了什么结果”

这和有限元软件本身的概念也一致：

- 输入文件主要定义模型
- 输出结果文件主要定义结果

## 6. 建议新增的接口

建议新增一个统一入口，例如：

- `POST /solver/run_and_parse`

这个名字的重点是：

- `run`：先计算
- `parse`：再接入现有解析系统

它不是替代 `/api/projects`，而是站在更上层做编排。

## 7. 建议请求参数

建议第一版至少支持下面这些字段：

```json
{
  "project_id": 1001,
  "input_file": "D:/data/model.inp",
  "job_name": "case_a",
  "result_group": "case_a_result",
  "async_submit": true,
  "solver_options": {
    "cpus": 8,
    "timeout_sec": 7200,
    "extra_args": []
  }
}
```

### 7.1 必填字段

- `project_id`
- `input_file`

### 7.2 推荐字段

- `job_name`
- `result_group`
- `async_submit`

### 7.3 可选字段

- `solver_options`
- `display_name`
- `step`
- `frame`
- `field_prefix`

说明：

- `step / frame / field_prefix` 主要对 Abaqus `.odb` 结果追加更有用
- 对 Nastran `op2` 可以先不强制要求

## 8. 文件类型识别规则

新接口收到文件后，先按后缀识别：

- `.inp` -> Abaqus 主链路
- `.bdf` -> Nastran 主链路

第一版建议只支持这两种输入。

如果不是这两种，直接报错，例如：

- “仅支持 inp 和 bdf 作为统一计算入口”

这样边界最清楚，避免第一版把：

- `odb`
- `op2`
- `f06`

这些结果文件也混进来。

## 9. 推荐完整流程

## 9.1 INP -> Abaqus -> ODB -> 项目结果组

### 后端流程

1. 收到 `inp`
2. 检查 `project_id` 对应项目是否存在
3. 若不存在，则调用 `POST /api/projects`
   - `source_type=inp`
   - `source_path=<inp path>`
4. 轮询项目状态，等待 `geom_status=ready`
5. 调用 Abaqus 求解
6. 拿到 `.odb`
7. 调用 `POST /api/projects/{project_id}/results`
   - `source_path=<odb path>`
   - `result_group=<result_group>`
8. 轮询结果组状态，直到 `ready`
9. 返回项目、结果组、产物路径、状态摘要

### 复用点

- 项目创建：`/api/projects`
- 结果挂载：`/api/projects/{project_id}/results`
- 求解调用：`run_abaqus_job()` 或现有 Abaqus 封装

## 9.2 BDF -> Nastran -> OP2 -> 项目结果组

### 后端流程

1. 收到 `bdf`
2. 检查 `project_id` 对应项目是否存在
3. 若不存在，则调用 `POST /api/projects`
   - `source_type=bdf`
   - `source_path=<bdf path>`
4. 轮询项目状态，等待 `geom_status=ready`
5. 调用 Nastran 求解
6. 拿到 `.op2`
7. 调用 `POST /api/projects/{project_id}/results`
   - `source_path=<op2 path>`
   - `result_group=<result_group>`
8. 轮询结果组状态，直到 `ready`
9. 返回项目、结果组、产物路径、状态摘要

### 复用点

- 项目创建：`/api/projects`
- 结果挂载：`/api/projects/{project_id}/results`
- 求解调用：`run_nastran_sol103_job()` 或后续统一 Nastran run 封装

## 10. 为什么要先建项目，再跑结果解析

这个顺序很重要。

因为结果解析不是孤立动作，它依赖“这个结果属于哪个项目的几何”。

比如：

- Abaqus 的 `odb` 结果要知道挂到哪个 `project_id`
- Nastran 的 `op2` 结果也要知道挂到哪个 `project_id`

如果不先建项目，后面的结果文件就没有稳定落点。

可以把它理解成：

- 项目是“盒子”
- 结果组是“往盒子里再放一份结果”

盒子都没建好，结果就没地方挂。

## 11. 建议返回结构

同步模式下，建议返回：

```json
{
  "workflow": "run_and_parse",
  "project_id": 1001,
  "source_type": "inp",
  "solver_type": "abaqus",
  "job_name": "case_a",
  "project_status": "ready",
  "result_group": "case_a_result",
  "result_group_status": "ready",
  "artifacts": {
    "input_file": "D:/data/model.inp",
    "result_file": "D:/data/case_a.odb"
  }
}
```

异步模式下，建议返回：

```json
{
  "task_id": "xxx",
  "status": "submitted",
  "task_type": "solver.run_and_parse"
}
```

## 12. 强烈建议默认走异步

原因很实际：

1. 求解器运行可能很久
2. 结果文件可能很大
3. 后面还要再跑一次解析

如果做成同步：

- 请求会卡很久
- 前端体验差
- 后端更容易超时

所以建议：

- 接口支持同步和异步
- 前端默认走异步
- 后端任务状态复用 `webapi/background_jobs.py`

位置：

- [webapi/background_jobs.py](/D:/WorkSpace/OtherProjects/VirtualReal702/webapi/background_jobs.py)

建议不要把所有逻辑全塞到路由函数里。

### 13.1 路由层

位置建议：

### 13.2 服务层

位置建议：

- `services/model_update/analysis/solver_service.py`

## 14. 统一编排伪代码

```python
def run_solver_and_parse_project_result(...):
    source_type = detect_from_suffix(input_file)

    if source_type == "inp":
        ensure_project(project_id, source_path=input_file, source_type="inp")
        wait_project_ready(project_id)

        solver_result = run_abaqus_job(...)
        odb_path = solver_result["solver"]["artifacts"]["odb"]

        upload = add_project_result_group(
            project_id=project_id,
            source_path=odb_path,
            result_group=result_group,
        )
        wait_result_group_ready(project_id, result_group)
        return build_response(...)

    if source_type == "bdf":
        ensure_project(project_id, source_path=input_file, source_type="bdf")
        wait_project_ready(project_id)

        solver_result = run_nastran_sol103_job(...)
        op2_path = solver_result["solver"]["artifacts"]["op2"]

        upload = add_project_result_group(
            project_id=project_id,
            source_path=op2_path,
            result_group=result_group,
        )
        wait_result_group_ready(project_id, result_group)
        return build_response(...)

    raise ValidationError("unsupported input file type")
```

## 15. 状态流转建议

统一接口虽然对外是“一次调用”，但内部其实有两段状态。

### 15.1 项目几何状态

复用现有：

- `pending`
- `running`
- `ready`
- `error`

### 15.2 结果组状态

复用现有：

- `pending`
- `running`
- `ready`
- `error`

### 15.3 新接口自己的任务状态

如果走 `background_jobs`，建议用：

- `submitted`
- `running`
- `succeeded`
- `failed`

这样前端看起来会很清晰：

- 大任务状态：这个“计算并解析任务”是否完成
- 项目状态：几何是否准备好
- 结果组状态：结果是否挂载好

## 16. 第一版建议边界

为了先把主链路打通，建议第一版收紧范围。

### 16.1 建议先支持

- 本地文件路径输入
- `inp -> abaqus -> odb -> result_group`
- `bdf -> nastran -> op2 -> result_group`
- 异步任务查询

### 16.2 建议先不做

- 同一个接口同时支持上传和远程 URL
- `odb` / `op2` 直接作为统一入口
- PBS 远程求解统一接入
- 多结果文件自动识别
- 自动重试复杂策略

原因不是这些以后不做，而是第一版先把“主干跑通”更重要。

## 17. 风险与注意点

### 17.1 不要重复创建项目

如果 `project_id` 已经存在，需要先定义策略：

- 如果项目不存在：创建
- 如果项目已存在且几何已 ready：复用
- 如果项目在 running：拒绝或等待
- 如果项目 error：是否允许重建，要明确

第一版建议：

- `ready` -> 复用
- `pending/running` -> 返回冲突错误
- `error` -> 暂不自动清理重建，先显式报错

### 17.2 result_group 命名要稳定

建议提供：

- 用户显式传 `result_group`

如果用户没传，再自动生成：

- `solver_result_<job_name>_<timestamp>`

否则以后前端查结果时不容易定位。

### 17.3 Nastran 结果文件不一定总是只有一个 OP2

第一版建议先约定：

- 默认取主 `op2`
- 如果发现多个候选，明确报错或按规则选第一个

不要悄悄猜。

### 17.4 同步等待超时要可控

无论是等项目 ready，还是等 result_group ready，都要有超时参数。

不然一旦某步卡住，接口会一直挂死。

## 19. 对前端的影响

前端其实会更简单。

前端只需要做两件事：

1. 发起一次“计算并解析”请求
2. 轮询任务状态，完成后拿 `project_id` 和 `result_group`

后面的模型查看、云图查看、结果切换，仍然走当前已有接口，不需要另学一套。

## 20. 最终建议

最终建议是：

1. 新接口放在 `webapi/routers/solver.py`
2. 新逻辑放在 `services/model_update/analysis/solver_service.py`
3. 项目几何一律复用 `POST /api/projects`
4. 求解结果一律复用 `POST /api/projects/{project_id}/results`
5. 第一版只支持 `inp` 和 `bdf`
6. 第一版默认推荐异步

一句话概括就是：

**不要重做解析系统，而是做一个“求解器 + 现有解析接口”的统一编排层。**

这样后面你再继续扩：

- 上传版
- PBS 版
- 批量任务版
- 自动命名版

都会顺很多。
