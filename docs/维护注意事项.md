## 1. result_blocks 表 result_group 打标失败（2026-07-16）

### 症状

某个 project 下，`/meta/overview` 和云图（`frame-colors`）一切正常，但以下接口全部查空或报错：

- `GET /fields?instance=...&step=...&result_group=...` → `fields: []`
- `POST /results/node-table`、`POST /results/node-time-value` → 400 `Field 'X' does not have NODAL position ...`
- `GET /api/projects/{id}/result-catalog` → 每个字段的 `instances` 都是 `[]`

判别方法：`python tools/diag_manifest.py <workspace目录>`，如果输出里 `result_blocks` 的行都是 `result_group=None`、而 `steps`/`result_files` 是 `default_result`，就是这个问题。

### 根因

壳单元结果按截面点（section point，sp1=底面、sp5=顶面）分块，旧版 `result_blocks` 表主键没有 `sp_num` 列，同一单元类型的多个 sp 块成了"重复行"（`result_group` 为 NULL 时 SQLite 唯一索引把 NULL 视为互不相等，重复行得以共存）。ODB 解析完成后 `job_runner` 给全表打 `result_group` 标签的 UPDATE 撞主键整条失败，旧代码还把异常静默吞掉（`except: pass`），于是 `result_blocks` 全表永远留在 NULL，L3 按 result_group 查询永远落空。

2026-07-16 已修（commit `e567cd0`）：主键加入 `sp_num`；打标前自动做 schema 迁移；打标失败会写 warning 到 job_logs，不再静默。**修复后新建的工程不会再出这个问题。**

### 存量工程修复

修复代码上线**之前**创建的工程（含壳单元结果的都可能中招），每个 workspace 跑一次：

```powershell
python tools/fix_result_blocks.py "<workspace目录>" --tag-null default_result
```

- 只重建 manifest.db 里的 `result_blocks` 索引表（迁移 schema + 打标），HDF5 数据本身没坏，**不需要重跑 L1/L2**
- 幂等，跑多次无害
- 不需要重启服务（manifest.db 每个请求都重新读）
- `--tag-null` 的值：ODB 直出的几何管道用 `default_result`；单独上传的结果组一般不需要 `--tag-null`（它们打包时就带标签）

### 相关的第二个坑：结果 HDF5 路径不能按 result_group 猜

adopt 型 `default_result`（几何管道直出的 ODB 结果）打包时 `result_group` 还是 NULL，结果文件落在 `l1/results/` 根目录，**没有** `l1/results/default_result/` 子目录。所以解析结果文件路径必须优先查 manifest 的 `result_files.file_path`（权威路由），查不到才退回按约定拼路径。

统一入口：`ManifestRepo.result_h5_abspath(step, field, result_group)`。**新写 L3 代码需要定位结果 HDF5 时一律用它**，不要自己 `os.path.join(workspace, "l1", "results", result_group, ...)` 拼——那正是当年 node-table / node-time-value 修完打标后又 404 的原因。
