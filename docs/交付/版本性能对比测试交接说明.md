## 6 结果判断与内容检查

- **HTTP 总时间**包含后端处理与完整响应下载。
- **Backend processing time**取响应头 `X-Elapsed-Time-Ms`，更适合判断计算瓶颈及小响应性能。
- **first**是脚本本轮观察到的首次接口请求，不等于整站冷启动，也不等于浏览器首次打开的总时间。
- **repeat median**是排除首次请求后的重复请求中位数。
- 图例、统计和区域接口在主分类颜色请求之后测试，可能复用已有分类缓存。
- 两版按顺序运行，第二版仍可能受益于操作系统文件缓存；单轮小幅变化不宜直接认定为代码收益或回归。

检查正确性时，不只看 HTTP 200：

1. JSON 接口检查包体业务状态。
2. 边线检查 `X-Edge-Count`，并查看报告的 `Edge response checks`。
3. 新旧版本边数或区域标签不同，不计算该项性能提升比例。
4. 封闭区域的外轮廓为 0 可能合理；相同边数也不能代替逐坐标核对。
5. `frame-colors`、`color-code` 没有 `X-Cache` 头，不代表没有缓存；结合重复请求的后端耗时判断。

上轮发现并修复的问题：旧区域单元边线接口只读 `<instance>_surface.h5`，但两阶段 L2 已把边数据放入独立 `<instance>_edges.h5`，导致返回空数据。`717d665` 已修复读取路径并兼容旧布局。本次换更早基线后，要重新检查结果，不能默认旧版一定返回空边线。

API 基准不测浏览器最终绘制。当前前端已有 `4b6fc26` 的“先加载轮廓线再加载模型”改动；若要评价用户实际看到模型的速度，需要另做浏览器测试，分别记录轮廓出现和完整模型出现的时间。

## 8 中文简报生成方法

**脚本自动生成原始 CSV 和英文完整报告。中文简报目前按当轮数据另行整理，并非脚本自动生成。**

复用 `docs/交付/性能优化简报-20261015.md` 的结构，按本次日期另存新文件，避免覆盖历史结论：

1. 一段主要结论，说明哪些操作明显变快、哪些变化较小。
2. 模型导入与加载表，保留首次读取、重复读取、导入就绪、变形和动画的代表性数据。
3. 分类查看与云图表，选择材料、截面、图例、统计、边线和云图等关键操作。
4. 问题修复及后续建议，保留仍慢或略微变慢的项目。
5. 验证范围，写清模型、版本、样本次数、测试场景数、请求数及功能测试结果。

数据整理规则：

- 所有指标使用同一次完整测试的数据，不混用不同轮次。
- 从 CSV 的 `case`、`version`、`temperature`、`elapsed_ms` 等字段汇总。
- `temperature=repeat` 的 `elapsed_ms` 取中位数，除以1000转换为秒；首次请求单列。
- 导入指标通常是本轮单次观测，不包装成重复请求中位数。
- 耗时减少比例为 `(旧版耗时 - 新版耗时) / 旧版耗时 × 100%`；按原始数值计算，再四舍五入。
- 模型读取接口耗时不能写成浏览器实际打开耗时。
- 空结果不列为提速成果；数值较小或变化较小的操作避免夸大百分比。
- 测试场景数、请求数和功能测试通过数按本轮重新统计，不照搬上轮38项、264次、30项。
- 面向领导少用接口名和缓存术语，重点说明从多少秒减少到多少秒、用户少等多久。
