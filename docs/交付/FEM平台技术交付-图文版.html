一、平台全景：一个平台，两条主线

传统 FEM 后处理有三道墙：许可证墙、格式墙、规模墙。本平台把仿真结果发布成一个网页服务来打穿它们。

痛点具体表现本平台的破解
许可证墙后处理软件按席位收费，设计师/项目经理/甲方看不了结果发布成网页，浏览器直接看，免 license
格式墙Abaqus（INP/ODB）与 Nastran（BDF/OP2）互不兼容，多工况对比要手工转换上游 L1 统一归一化，四种格式一套管道
规模墙桌面客户端全量加载，千万节点内存爆、单帧几十秒离线预处理 + 二进制协议 + GPU 渲染

平台是一个 FastAPI 进程（app.py），内部并行跑两条主线，仅在"把修正量写回当成一个结果场"这一处耦合。

两条主线的唯一耦合点 主线二算出的"每个部件被改了多少"，会作为一个新的结果场写回主线一——评审因此可以像看应力云图一样， 在浏览器里直接看到这次修正动了模型的哪些地方。

二、主线一 · 端到端可视化管线

上传 → 解析 → 预处理 → 服务 → 渲染。一条单向、分层、无反向依赖的流水线，数据每过一层就换一次"形态"。

下面把这条链路拆成四个环节，每个环节都从五个维度讲： 难点 思路 实现 结构 效果。

2.1 环节一：多格式上传与忠实提取 L1

难点

Abaqus 与 Nastran 是两套"方言"（单元命名/坐标系/结果组织都不同）；ODB 是私有二进制，只能用受限的 Abaqus Python 2.7 读，还装不了 h5py、占 license。

思路

在最上游就把格式差异"焊死"成同一套内部表示（HDF5 + manifest.db 路由）。新增格式只加一个 L1 适配器，其他层零改动。ODB 用两阶段拆分隔离 license。

实现

受限环境只"读"（导出 .npy），标准环境只"写"（打包 HDF5），中间用临时文件交接。忠实原则：只搬运不加工，保留全部原始精度。

结构

src/l1/：abaqus_dump / l1_pack / inp_pack / bdf_pack / op2_pack / cdb_pack / rst_pack；manifest_schema 定义路由表。

效果

四格式四工作流统一接入；几何与结果解耦，可多工况追加；license 严格隔离在提取阶段。

manifest.db —— 路由中枢 L3 运行时从不扫描文件系统，任何"这个字段在哪个文件的哪个路径"都是一次 SQLite 查询。这也是"新增格式零改动其他层"的技术基础。

2.2 环节二：预处理与渲染缓冲预构建 L2

难点

L1 存的是含大量内部面的完整体网格，GPU 只认三角面；千万单元逐面判断内外，Python 循环要跑几小时；还要算特征边否则模型没棱角。

思路

把计算密集的活儿一次性搬到离线阶段，NumPy 全程向量化，算好的缓冲存 HDF5，L3 只读不算——"计算"与"服务"彻底分家。

实现

面哈希去重（出现1次=表面，2次=内部面丢弃）；向量化三角化；索引几何；特征边；八叉树；并查集划分均化域。

结构

src/l2/ingest.py 一个文件跑完整条 L2（约1600行），输出 surface.h5 / render.h5 并回填 manifest.db。

效果

百万单元分钟级完成；云图切换只重传颜色；特殊单元一并提取不再"看不见"。

设计演进 · Triangle Soup → 索引几何 最初设计每个三角形三顶点完全独立（Triangle Soup），实测内存太大，改为同一单元面内共享顶点的索引几何， 内存降到 1/3~1/2，同时保留跨单元面的"硬边"效果。均化域子系统用并查集分组，决定平滑着色"平滑得对不对"。

2.3 环节三：按需数据服务 L3

难点

多 worker 每个各存 2GB 索引就是 8GB；大数组用 JSON 传体积膨胀 33%；HDF5/SQLite 单写多读，算与读的进程要并行不打架。

思路

内存靠 fork+写时复制共享；传输靠自研二进制协议 L3BE；并发靠读写分离——写活儿全交给独立后台 job_runner，靠状态机同步。

实现

label→行号用排序数组+searchsorted（不用 dict，能被多进程真共享）；L3BE 一个响应装多段异构数组；抢占任务用一条原子 SQL。

结构

src/l3/：api/routes（15文件~70端点）· services（>1万行）· infra（DB+l3be+runner）· core（config/state/errors）。

效果

4 worker 内存≈单 worker（2GB）；千万顶点端到端<2秒；新项目10秒内热加载不重启。

2.4 环节四：浏览器 GPU 可视化 前端

难点

在浏览器（CPU 很弱）里对千万三角面做到拾取毫秒响应、振型60fps动画、云图/变形/截面实时交互。

思路

能交给 GPU 的绝不让 CPU 算：几何永驻显存；云图只更新颜色；动画在着色器里算；拾取用 BVH 把 O(N) 降到 O(log N)。

实现

模态动画 d(t)=Re·cos(ωt)+Im·sin(ωt) 写进顶点着色器，CPU 每帧只更新一个时间变量；拾取命中后服务端 O(1) 反查读 L1 精确原始值。

结构

viewer/（Vue3+Three.js+Pinia+Vite）：ThreeViewport 统管场景对象 + 各功能卡片。

效果

拾取<100ms；动画60fps与规模无关；云图切换<500ms；免安装免license。

后端优先原则前端实际嵌入在第三方项目里、发布成本高，因此平台设计原则是优先在后端消化问题、尽量不改前端。

三、核心技术难点专题

第 2 章讲"正常流程"，这一章讲真正的硬骨头——那些"不报错、但结果悄悄错了"的坑，最能体现工程功力。

3.1 应力云图数值口径与商业软件严格对齐 最难

云图上的"应力值"不是仿真直接吐的数字，而是从单元内部"积分点"的原始张量，经过外推、算 Mises/主应力/不变量、正负号处理算出来的。Abaqus 这套口径是不公开的"潜规则"，任何一步差一点，云图就偏离 3%~5%，而且不报错——只能靠对照脚本逐值比对揪出来。真实踩过的坑：

  • Mises 是非线性量，"先在积分点算 Mises 再外推" ≠ "先外推张量再算"，前者会算出物理上不可能的负 Mises；
  • 第三不变量 INV3 漏了系数与开方；"Abs 变体"应取"绝对值更大的主应力但保留符号"；
  • 应变剪切分量是工程剪应变 γ=2ε，算不变量前要 ÷2 还原，且应变不该算 Mises；
  • 官方分量名 MAX_INPLANE_PRINCIPAL（无下划线）被误写成有下划线，导致面内不变量从没生成过。

所有公式集中在 src/l1/abaqus_dump.py::_compute_invariants_numpy，配 docs/l1/不变量计算公式表.md 做公式台账逐条记录修正历史，并有回归测试固化。

四、主线二 · 模型修正闭环

可视化解决"看结果"，这条主线解决"结果不准怎么办"——用试验数据自动校准仿真参数，让仿真越来越接近现实。

三个技术要点

  • 试验-仿真配准：传感器坐标系与仿真节点坐标系往往不重合、有安装误差，用 ICP 迭代最近点自动刚体配准（支持仅平移 / 平移+旋转），再用八叉树最近邻落点，超容差允许剔除。
  • 灵敏度不是"试出来"的：不用有限差分，而是生成 Abaqus DSA / Nastran SOL200 专用输入，调用求解器自身的解析灵敏度能力，精度更高。三级映射链路 d_U_1 → 参数序号 → 参数名 → INP Section 是最容易困惑的地方。灵敏度矩阵做无量纲归一化（因为弹性模量 1e11 和壳厚 1e-3 数量级天差地别），反演才稳定。
  • 贝叶斯参数估计（注意：不是机器学习里的"贝叶斯优化"）：用参数先验协方差+响应观测协方差构造增益矩阵（本质最小方差估计/类卡尔曼滤波），加 Tikhonov 阻尼防病态，参数夹到物理上下界。之所以不用遗传算法——有精确梯度时十几次就收敛，无梯度方法要几百上千次。
多求解器统一主线二后扩展支持 Nastran（BDF/OP2）和 Ansys（CDB/RST），做法是"归一化 model dict + 统一落库函数"——无论数据来自哪个求解器，元数据落到同一批 MySQL 表，下游灵敏度/贝叶斯完全不区分来源。所有耗时操作走"提交任务→轮询状态"的异步模式。

六、最终达成的效果

从四种格式原始文件到浏览器三维交互后处理的完整贯通，并叠加模型修正闭环。

格式支持Abaqus INP/ODB、Nastran BDF/OP2（含/不含嵌入几何）、Ansys CDB/RST；自动识别 + 一致性校验
模型规模≤ 1000 万节点、数十装配实例、数十分析步、数百帧
免许可证INP/BDF/OP2 全链路免 license，ODB 仅提取阶段需要

功能清单

三维旋转/平移/缩放 · 透视/正交切换 · 结果云图（平滑/平面着色）· 自定义图例区间 · 变形显示（nlgeom 自动锁定）· 单元/节点精确拾取（返回 ODB 原始标签与结果值）· 包围框区域选择 · 多点探针表格 · 截面切割（X/Y/Z，含填充与着色）· 模态振型动画（GPU/CPU 双模式）· 特征边线框 · 梁杆线单元 / 质量点 / 耦合蜘蛛线渲染 · 结果分量选择 · 多工况结果组切换 · 用户自定义集合 · 模型修正闭环（ICP 配准 / DAC-DSF-MAC / DSA 灵敏度 / 贝叶斯迭代 / 修正效果云图回写）。

工程方法论沉淀 项目最有价值的沉淀是一套"逐位对齐 + 对照脚本 + 回归测试"的方法论：对每个"不报错但会悄悄错"的数值口径问题（不变量公式、混合模型交并集、高阶单元峰值、Nastran 坐标系），都通过独立对照脚本逐值比对商业软件、定位修复、再用回归测试固化——避免同一个坑踩第二次。这比任何单一功能都更能体现团队真功夫。
