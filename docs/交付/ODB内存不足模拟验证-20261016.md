# ODB 内存不足模拟验证

更新时间：2026年10月16日

**已确认：内存不足时，真实 runner 会停止后续打包，前端使用的 HTTP 接口能读到明确失败原因。**
本次还修复了实际联调发现的问题：状态轮询曾意外创建空 `manifest.db`，使后续结果目录接口报 500。
修复后，4 个故障场景、12 次 HTTP 状态查询全部通过，相关 24 项回归测试全部通过。

## 实际验证方式

使用真实 Abaqus Python 3.10 / NumPy 1.22.4 加载当前导出脚本的 `_main_checked`，
只将其 `main` 替换为会抛出内存异常的函数；runner 子进程是真实进程，没有伪造 stdout 或返回码。
NumPy 场景使用真正的 `_ArrayMemoryError((9674696,), dtype('int64'))`，错误文本与原截图一致：
无法为 9,674,696 个 int64 分配 73.8 MiB。

父进程使用真实 `job_runner.py`、真实 SQLite 注册库和项目路由，启动仅绑定本机 127.0.0.1 的
独立 HTTP 服务，然后发出实际 GET 请求。每个场景使用全新项目和工作区；未打开原始 ODB，
未分配大数组，未向现有项目或模型修正数据库写数据。

业务基础提交为 `c77b345`，加本次 `_build_project_response` 查询修复；不是纯 `c77b345` 的通过记录。
归档时的源文件 SHA-256 见下方 CSV，运行 JSON 的 `commit` 表示当时的基础 HEAD。
独立服务只挂载项目路由，不包含正式应用的其他模块、预加载或模型修正启动流程。

## 结果

| 场景 | 实际启动器退出码 | 项目几何状态 | 结果组状态 | 后续打包 | HTTP 查询 |
|---|---:|---|---|---|---|
| 首次解析：Python `MemoryError` | 0 | error | error | 未启动 | 3 次通过 |
| 首次解析：NumPy `_ArrayMemoryError` | 0 | error | error | 未启动 | 3 次通过 |
| 首次解析：NumPy 异常并强制返回 0 | 0 | error | error | 未启动 | 3 次通过 |
| 追加结果：NumPy 异常并强制返回 0 | 0 | ready | error | 未启动 | 3 次通过 |

前两个场景没有主动强制成功码，Abaqus Windows 启动器仍实际返回了 0，复现了原故障中的返回码失真。
runner 根据错误和缺少完成标记判定失败，而不是只依赖启动器退出码。
追加场景使用测试内存中的已有几何索引占位，只验证几何状态保持 ready、对应结果组失败，未验证真实几何渲染。

每个场景分别请求：

- `GET /api/projects/{project_id}`
- `GET /api/projects`
- `GET /api/projects/{project_id}/result-catalog`

12 次请求均为 HTTP 200、包体 `code: 200`，表示状态查询成功。解析失败由 `geom_status` 和结果组
`status` 表示，原因位于 `result_groups[].error_message`，包含原始异常和下面这句明确提示：

> ODB 提取内存不足：已停止后续打包。请释放其他程序/已加载模型的内存，检查 Windows 虚拟内存，或换用内存更大的机器重试。

每个场景都只启动了一次导出子进程，没有启动打包或 L2，没有收到 `ODB_DUMP_COMPLETE`，
也没有生成 `manifest.db`。返回原因不包含 `dump_meta.json not found`，未被误报成几何一致性校验失败。

## 联调发现并修复的问题

原 `_build_project_response` 为读取一致性校验方式，在提取还没有生成 manifest 时也访问
`ManifestRepo`；SQLite 会创建空文件。状态查询把该异常吞掉，表面上正常返回；下一次结果目录查询
看到文件存在，继续读 `steps` 表，最终报 `sqlite3.OperationalError: no such table: steps`。

现改为先检查 manifest 是否存在，不存在时从注册库/解析选项读取状态，避免创建空文件。
补强的回归测试使用真实 ManifestRepo，明确检查查询失败项目后没有新建 manifest；
此前只用假对象抛异常，无法发现这个副作用。接口路径、参数和 JSON 结构保持原有约定。
