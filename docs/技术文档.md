## 一、项目背景与应用需求

### 1.1 行业背景

有限元分析（Finite Element Method，FEM）是现代工程结构设计与验证的核心计算手段，广泛应用于航空航天、轨道交通、能源装备、汽车、桥梁等领域的强度、模态、屈曲、热-结构耦合等仿真分析。

随着精细化设计需求的提升，工程模型规模持续增长：

- **节点规模**：早期典型模型为数万节点；当前精细化模型普遍达到百万至千万量级节点，全机/全车有限元模型甚至突破亿节点。
- **载荷工况**：单个分析任务通常包含数十个子工况（load case），每个工况产生独立帧序列，一次提交产生的仿真结果文件大小可达数十 GB。
- **求解器多元化**：工程实践中，Abaqus 与 Nastran 是两大主流商业求解器，各有其擅长领域（Abaqus 在非线性、Nastran 在线性动力学），同一项目的不同分析阶段可能分别使用不同求解器，数据格式存在显著差异。

仿真结果数据（Abaqus ODB 文件、Nastran OP2 文件等）是结构验证链路的核心输出物，其中包含完整的几何拓扑信息与多步骤、多帧的物理场数值（位移、应力、应变、反力等），是设计优化决策和工程评审的直接依据。

### 1.2 现有工程问题

面向大规模、多求解器 FEM 仿真结果的后处理，现有工具链面临以下系统性工程限制：

**（1）许可证依赖制约协同访问**

现有主流后处理工具（Abaqus CAE、HyperView、Femap、Patran）均采用商业许可证授权模式，单席位许可证成本高昂。工程团队中仅少数人持有许可证，导致大量参与评审的人员（设计师、项目管理者、客户）无法直接访问仿真结果，严重制约了数据流通效率。

**（2）跨求解器格式壁垒**

Abaqus（INP/ODB）与 Nastran（BDF/OP2）格式相互不兼容，既无通用读取标准，也无统一的数据管理体系。工程师在多格式数据之间切换时，需要在不同工具间手动转换、重新提交，数据一致性难以保障，工况对比分析尤为困难。

**（3）大规模数据处理能力不足**

桌面客户端采用全量加载模式，在处理千万节点、多帧结果时内存占用极高，响应迟缓（单帧云图渲染等待时间可达数十秒），难以支撑工程评审现场的实时交互需求。

**（4）非线性大变形显示缺乏规范约束**

几何非线性分析（nlgeom=True）中，结构变形量纲与几何尺寸同阶，变形比例因子必须设为 1 才能正确表达结构响应。现有工具缺乏对该分析类型的自动识别与比例因子约束机制，操作失误可能导致误读变形幅度。

**（5）访问模式受限**

桌面客户端无法提供轻量级的网络访问接口，仿真结果无法面向浏览器或移动端进行查阅，不适应分布式团队协作与远程评审的工作模式。

### 1.3 建设必要性

针对上述问题，构建一套面向通用 FEM 后处理需求的 Web 化、多格式统一服务平台，具备以下核心建设价值：

- **降低访问门槛**：将仿真结果发布为 HTTP 服务，任意浏览器均可访问，免除许可证限制；
- **打通格式壁垒**：统一接入 Abaqus 与 Nastran 两大主流求解器的输入/输出格式，数据在同一平台管理与对比；
- **支撑大规模实时交互**：通过预处理离线计算 + 二进制协议 + GPU 渲染的组合，实现千万节点量级模型的流畅浏览器交互；
- **规范化结果呈现**：对大变形分析自动锁定比例因子，对模态分析自动播放谐波动画，减少人工配置错误。

## 二、数据对象与场景分析

### 2.1 支持的文件格式

平台统一支持 Abaqus 与 Nastran 两大求解器体系的四种主流文件格式。所有格式经格式适配层（L1 提取模块）转换为相同的内部 HDF5 + SQLite 存储结构，进入统一的 L2 预处理与 L3 服务流水线。

| 格式 | 求解器 | 类型 | 内容 | 依赖工具 | 许可证 |
|---|---|---|---|---|---|
| **INP** | Abaqus | 输入文件 | 几何（节点、单元、集合、截面定义） | 纯 Python | 无需 |
| **ODB** | Abaqus | 输出数据库 | 几何 + 多步骤结果（U/S/E/RF 等全部字段） | Abaqus Python 2.7 | 需要（提取阶段） |
| **BDF** | Nastran | 散块数据文件 | 几何（节点、单元、属性、材料） | pyNastran（纯 Python） | 无需 |
| **OP2** | Nastran | 输出文件 | 结果（位移、模态振型）；含 GEOM1/GEOM2 时亦含几何 | pyNastran（纯 Python） | 无需 |

**说明**：

- INP 与 BDF 均为"几何专用"格式，本身不含仿真结果。使用这两种格式创建项目后，需追加对应的 ODB（Abaqus 结果）或 OP2（Nastran 结果）以获取云图数据。
- ODB 文件同时包含几何与结果，可作为独立项目一次提交。
- OP2 分为两种模式：`PARAM,POST,-1` 输出的 OP2 含嵌入几何（GEOM1/GEOM2 表），可作为独立项目；`PARAM,POST,-2` 输出的 OP2 为纯结果文件，需配合已有的 BDF 几何使用。

### 2.4 典型工程处理场景

**场景一：结构静力分析多工况云图查阅**

典型输入为 INP（几何）+ 多个工况 ODB（或 BDF + OP2），每套工况独立为一个结果组。工程师在浏览器中切换步骤与帧，查阅位移云图（U）、Mises 应力云图（S，MISES 分量），配合拾取工具获取危险区域节点/单元的精确结果值。

**场景二：模态分析振型评审**

输入为含 FREQUENCY 步骤的 ODB 或 Nastran SOL 103 OP2。平台自动识别分析类型，前端以谐波动画形式展示各阶振型（实部/虚部），支持频率显示与振型切换，无需逐帧网络请求。

**场景三：屈曲分析特征模态显示**

输入含 BUCKLE 步骤，各帧对应不同屈曲模态，前端以静态变形或连续动画形式展示结构失稳形态。

**场景四：几何非线性大变形结果显示**

ODB 中记录 nlgeom=True 标志。平台自动识别，将前端变形显示的比例因子强制锁定为 1（真实变形量），避免因比例放大导致变形幅度误判。

**场景五：多实例装配体整体查看**

包含多个零部件实例的装配体模型（各实例有独立坐标变换矩阵），平台在 L2 预处理阶段将所有实例坐标变换到全局坐标系，浏览器中呈现完整装配体的整体三维形态与云图结果。

**场景六：大模型截面内部结果分析**

对实体单元模型（如航空发动机轮盘、结构梁截面），通过截面切割工具（ViewCutCard）创建任意切面，在截面上展示内部应力/应变分布，用于评估内部危险区域。

## 三、系统总体目标

针对第一章所述工程问题，平台建设目标如下：

**总体目标**：建立面向通用有限元仿真结果的 Web 化、多格式统一、交互式后处理能力，实现从 Abaqus（INP/ODB）与 Nastran（BDF/OP2）原始仿真文件到浏览器三维云图交互的全流程数据贯通，支撑无许可证、跨平台的工程评审与结果查阅。

**分项能力目标**：

**目标一：多格式统一接入能力**

统一接入 Abaqus INP/ODB 与 Nastran BDF/OP2，经格式适配层（L1 提取模块）转换为相同的内部 HDF5 + SQLite 存储结构。L2 预处理与 L3 服务层对数据来源格式无感知，同一套渲染与查询逻辑适用于所有格式。Nastran 单元卡名自动映射为 Abaqus 等效单元类型，两套求解器体系的数据在统一管道内流转。

**目标二：几何忠实还原能力**

针对各格式的几何拓扑，忠实提取节点坐标、单元连接关系、实例坐标变换矩阵。支持壳单元、线性/高阶实体单元、梁/杆线单元、质量点的混合模型，高阶单元角节点参与渲染、完整高阶连接数据独立存档。所有实例坐标在 L2 阶段统一变换至全局坐标系，保障装配体整体几何的正确性。

**目标三：结果场映射与着色能力**

针对任意帧的结果字段（位移 U、应力 S、应变 E、反力 RF 及用户自定义场），支持多分量标量场提取（含张量主值、Mises 等效量、各方向分量），以逐顶点 RGBA 着色形式传输至浏览器，支持平滑着色（跨单元平均）与平面着色（单元常量）切换，提供精确图例区间（全局最小/最大值）。

**目标四：大规模实时渲染能力**

针对千万节点量级模型，通过以下机制实现流畅帧率的浏览器三维交互：预处理阶段离线完成表面提取与索引几何构建；采用二进制协议（L3BE）代替 JSON 传输大规模数组；前端 Three.js 以 WebGL GPU 渲染，不占用 CPU 计算资源；色彩更新仅需传输顶点颜色属性，不重新传输几何数据。

**目标五：空间查询与精确拾取能力**

面向工程评审中"点击查看具体数值"的需求，实现单元/节点级精确拾取（Pick）与包围框区域选择（BBox Select）。单次点击触发服务端从 L1 HDF5 读取该单元该帧的原始结果数值，返回精确值（非插值近似）。拾取响应在大规模模型下仍达到交互级延迟（< 100 ms）。

**目标六：模态动画能力**

针对频率分析（SOL 103/FREQUENCY 步骤）振型数据，在浏览器中实现实时谐波动画播放，帧率 ≥ 60 fps，支持任意阶振型切换与动画频率调节，无需逐帧网络请求。

**目标七：截面分析能力**

支持任意轴向切面（X/Y/Z），在截面几何上展示对应的结果场云图，用于获取模型内部的应力/应变分布，弥补表面渲染无法呈现内部状态的不足。

## 四、系统总体架构

### 4.1 整体架构

平台采用**三层流水线 + 前端**的总体架构，各层职责单一，数据单向流动，运行时无反向依赖：

```
多格式输入文件
  INP / ODB / BDF / OP2
         │
         ▼
┌────────────────────────────────────────────────────────────────┐
│  L1 — 格式适配与忠实提取层                                      │
│                                                                │
│  INP:  src/inp/ 解析器 → inp_pack.py          （无许可证）    │
│  ODB:  abaqus_dump.py（Abaqus Python 2.7）                    │
│        + l1_pack.py（Python 3 / h5py）        （需许可证）    │
│  BDF:  bdf_pack.py（pyNastran）               （无许可证）    │
│  OP2:  op2_pack.py / op2_geom_pack.py（pyNastran）（无许可证）│
│                                                                │
│  输出（所有格式统一）：HDF5 文件集 + manifest.db               │
└────────────────────────────┬───────────────────────────────────┘
                             │  一次性离线计算
                             ▼
┌────────────────────────────────────────────────────────────────┐
│  L2 — 预处理层（src/l2/ingest.py）                             │
│                                                                │
│  全局坐标变换 → 表面提取 → 三角化                              │
│  → 索引几何（positions + indices）                             │
│  → 特征边（边界边 + 折叠边 ≥30°）                             │
│  → 八叉树空间索引（max_depth=8，leaf≤1000）                   │
│                                                                │
│  输出：render.h5（逐实例渲染缓冲）                             │
└────────────────────────────┬───────────────────────────────────┘
                             │  按需读取
                             ▼
┌────────────────────────────────────────────────────────────────┐
│  L3 — 服务层（src/l3/，FastAPI + Gunicorn）                    │
│                                                                │
│  内存注册表（ModelIndex）：预 fork 加载坐标/拾取映射/八叉树    │
│  注册表轮询（10 s）：热加载新就绪项目                          │
│  嵌入式 Runner：job_runner 以后台线程管理 L1/L2 流水线         │
│                                                                │
│  HTTP API + L3BE 二进制协议                                    │
└────────────────────────────┬───────────────────────────────────┘
                             │  HTTP / WebSocket
                             ▼
┌────────────────────────────────────────────────────────────────┐
│  前端查看器（viewer/，Vue 3 + Three.js）                        │
│                                                                │
│  Three.js WebGL 渲染 │ BVH 加速拾取 │ 模态着色器动画           │
│  云图控制 │ 变形显示 │ 截面切割 │ 探针表格 │ 图例编辑           │
└────────────────────────────────────────────────────────────────┘
```

### 4.2 分层设计原则

**L1 承担许可证隔离与格式归一化**

所有与求解器专有格式相关的解析工作在 L1 完成，包括需要 Abaqus 许可证的 ODB 提取。L1 完成后，后续所有层均与原始格式无关。这使得 L2、L3、前端可以独立开发和测试，也使得添加新格式（如 OP2）只需新增一个 L1 提取器，无需改动其他层。

**L2 承担计算密集的离线预处理**

表面提取、三角化、特征边计算、八叉树构建均属于计算密集型操作（百万单元模型耗时分钟级），不应放在服务请求路径上。L2 将这些计算结果持久化为 HDF5 文件，L3 服务期间只读，彻底分离"计算"与"服务"两个阶段。

**L3 承担轻量按需服务**

L3 的每次请求仅做"查表 + 切片 + 打包"，读取预构建的几何缓冲（L2 HDF5）和结果数据（L1 HDF5），经 L3BE 二进制打包后返回。服务进程自身不持有文件句柄，而是按请求打开关闭，避免长连接占用文件锁。

**前端承担渲染与交互**

几何数据接收后永驻 GPU 缓冲（`BufferGeometry`），色彩更新仅通过顶点颜色属性（`color` attribute）传输差量，不重传几何。BVH 在加载时一次构建，支持后续所有拾取操作。

### 4.3 并发与数据一致性模型

| 关系 | 机制 | 说明 |
|---|---|---|
| L1 写 ↔ L3 读 | 状态机隔离 | manifest.db 中的 geom_status/result_status 字段控制 L3 加载时机；job_runner 写完后才更新状态为 ready |
| 多 Worker ↔ 内存索引 | fork + CoW | Gunicorn 主进程 pre-fork 加载完内存后再 fork Worker；Worker 以 copy-on-write 共享只读内存 |
| 多 Worker ↔ SQLite | 只读 | L3 对 manifest.db 只读（user_sets 写入除外）；写入由 job_runner 单进程负责 |
| 多 Worker ↔ HDF5 | 只读 | HDF5 多读者并发安全；L3 不写 HDF5 |
| 注册表轮询 | daemon 线程 | 每 Worker 各自独立的 daemon 线程轮询 registry.db，感知新就绪项目并热加载 |

### 4.4 项目生命周期

每个 FEM 项目在系统内经历以下状态迁移：

```
提交（POST /api/projects）
        │
        ▼
   geom_status = pending
        │
        ▼（L1 提取执行中）
   geom_status = l1_running
        │
        ▼（L1 成功）
   geom_status = l1_done
        │
        ▼（L2 预处理执行中）
   geom_status = l2_running
        │
        ▼（L2 成功，项目几何就绪）
   geom_status = ready ←── L3 注册表轮询发现后热加载
        │
        │（追加结果组：POST /api/projects/{id}/results）
        ▼
   result_group.status = pending → l1_running → ready
```

几何就绪后即可在浏览器中查看模型轮廓与线框；结果组就绪后才能查看云图。

## 五、功能模块设计

### 5.1 多数据源接入模块（格式适配层）

**工程目标**：为不同求解器格式提供统一的接入入口，屏蔽格式差异，使后续处理层对数据来源无感知。

#### 5.1.1 接入入口与格式识别

前端或上游系统通过 `POST /api/projects` 提交文件路径与格式声明：

```json
{
  "project_id": "uuid-xxxx",
  "source_path": "/data/uploads/model.bdf",
  "source_type": "bdf"   // 可选，不传时按扩展名自动推断
}
```

`source_type` 取值：`inp` / `odb` / `bdf` / `op2`。服务端按扩展名（`.inp`/`.odb`/`.bdf`/`.op2`）自动推断，亦可由调用方显式声明（两者均提供时做一致性校验）。

OP2 提交时，服务端额外扫描文件头部二进制内容（前 64 KB），检测是否含有 `GEOM1` / `GEOM2` 表标记，自动区分"含嵌入几何（模式 D）"与"纯结果（模式 C）"两种子模式，无需调用方声明。

#### 5.1.2 四种工作流模式

| 模式 | 几何输入 | 结果输入 | 许可证要求 | 典型使用场景 |
|---|---|---|---|---|
| **A — ODB 单文件** | ODB（含几何） | ODB（同文件） | 需要（提取阶段） | Abaqus 全流程，几何与结果一体 |
| **B — INP + ODB** | INP（几何） | ODB（追加结果组） | 需要（结果追加） | 几何来自输入卡，多批次结果分析 |
| **C — BDF + OP2** | BDF（几何） | OP2（追加结果组） | 无需 | Nastran 全流程，免许可证 |
| **D — OP2 单文件** | OP2 内嵌（GEOM1/GEOM2） | OP2（同文件） | 无需 | PARAM,POST,-1 输出，单文件覆盖 |

#### 5.1.3 几何与结果分离机制

模式 B 与 C 将几何与结果分离处理：

1. **几何阶段**：提交 INP 或 BDF，触发 L1 几何提取 + L2 预处理，完成后 `geom_status = ready`，此时浏览器可查看模型轮廓。
2. **结果追加**：通过 `POST /api/projects/{id}/results` 提交结果文件（ODB 或 OP2），每次追加一个命名结果组（result_group），包含独立的步骤/帧/字段元数据。
3. **一致性校验**：结果追加时，服务端自动比对结果文件中的实例名称、节点数、单元数与几何 manifest.db 中的记录，不匹配则拒绝导入，避免错配。
4. **多结果组**：同一几何可追加多套结果，例如不同工况、不同求解批次，浏览器中可切换查看。

#### 5.1.4 URL 远程文件支持

`source_path` 支持 HTTP(S) URL，服务端在处理前自动下载至本地临时路径，适用于文件存储于对象存储（OSS/S3）或其他服务器的场景。

### 5.2 L1 提取模块（`src/l1/`）

**工程目标**：将各格式原始文件忠实转换为统一的内部 HDF5 + manifest.db 存储结构，不做坐标变换或数值裁剪，保留全部原始精度。

#### 5.2.1 INP 提取路径

**入口**：`src/l1/inp_pack.py`  
**核心依赖**：`src/inp/`（自研 Abaqus INP 解析器，纯 Python）

`src/inp/` 解析器架构：

| 模块 | 职责 |
|---|---|
| `lexer.py` | 词法分析：处理 `*INCLUDE` 文件展开、注释过滤（`**`）、续行符（`,` 末尾）、大小写归一化 |
| `parser.py` | 语法分析：按 `*KEYWORD` 层次构建 AST，识别关键字参数（`ELSET=xxx`） |
| `model.py` | 数据模型：节点集合（`*NODE`）、单元集合（`*ELEMENT`）、几何集（`*NSET`/`*ELSET`）、截面（`*SHELL SECTION`/`*SOLID SECTION`） |
| `resolver.py` | `*INCLUDE` 路径解析：相对路径相对于主文件目录展开，支持嵌套 include |
| `exporter.py` | L1 HDF5 写入：将解析后的模型对象写入标准几何 HDF5 结构 |

INP 格式只含几何信息（节点坐标、单元连接、集合定义、截面属性），不含任何仿真结果。

#### 5.2.2 ODB 提取路径

**入口**：`src/l1/abaqus_dump.py`（Phase 1）+ `src/l1/l1_pack.py`（Phase 2）  
**核心依赖**：Abaqus Python 2.7 内置 `odbAccess`（Phase 1）；`h5py`（Phase 2）

**Phase 1 — abaqus_dump.py**（需 Abaqus 许可证）

在 Abaqus Python 2.7 环境下运行，调用 `odbAccess` API：

- 遍历 ODB 中所有 Instance，提取节点坐标（`instance.nodes`）、单元连接（`instance.elements`）、实例坐标变换（`instance.transform`）；
- 遍历所有 Step → Frame → FieldOutput，按 position（NODAL/ELEMENT_NODAL/INTEGRATION_POINT）提取结果数组，转存为 `.npy` 临时文件；
- 提取 Assembly 级坐标系、全局集合（`*NSET`/`*ELSET`）成员关系；
- 记录 nlgeom 标志（`step.nlgeom`），写入 `step_meta.json`，供 L3 服务在变形显示时锁定比例因子；
- 支持 `--steps`/`--frames`/`--field-prefix` 参数进行选择性提取，减少大文件的处理时间。

采用行缓冲 stdout（`sys.stdout = os.fdopen(sys.stdout.fileno(), 'w', 1)`）确保进度日志实时输出，不因 Abaqus Python 缓冲而延迟。

**Phase 2 — l1_pack.py**（标准 Python 3）

读取 Phase 1 产生的 `.npy` 中间文件，打包写入 HDF5：

- 几何数据写入 `l1/geometry/<inst>.h5`（按实例）；
- 高阶单元完整连接写入 `l1/geometry/<inst>_highorder.h5`；
- 结果数据以 `[num_frames, N, num_components]` 三维张量布局写入 `l1/results/<result_group>/<step>__<field>.h5`，同一字段所有帧连续存储，支持单次 IO 读取任意帧切片；
- 更新 manifest.db 的 `steps`/`frames`/`result_files`/`result_blocks` 表；
- 支持结果分组（`--result-group`）追加模式：在几何已有的基础上追加新批次结果，不重写几何文件。

#### 5.2.3 BDF 提取路径

**入口**：`src/l1/bdf_pack.py`  
**核心依赖**：`pyNastran`（纯 Python，无需 Nastran 许可证）

处理流程：

1. 调用 pyNastran `read_bdf()` 读取 BDF 文件，解析 GRID 节点坐标、各类单元卡（CQUAD4、CHEXA 等）、属性卡（PSHELL、PSOLID）、材料卡（MAT1 等）；
2. 按预定义映射表（见 2.3 节）将每种 Nastran 卡名转换为等效 Abaqus 单元类型名称，归入统一的 `elements/<etype>/` HDF5 分组；
3. 实体单元（CHEXA/CPENTA/CTETRA）按节点数动态判断线性或高阶变体；
4. 为确保一致性，高阶单元（如 CQUAD8、CTETRA10）仅存储角节点连接至主 geometry h5，完整节点列表写入 `_highorder.h5`；
5. 生成 assembly.h5（单实例，无坐标变换）和 sets.h5（从 BDF SET 卡提取）；
6. 更新 manifest.db 的 `instances` 与 `element_type_dist` 表；
7. 提取完成后自动触发 BDF 数据导入模型修正服务（可选）。

#### 5.2.4 OP2 提取路径

**入口**：`src/l1/op2_geom_pack.py`（含嵌入几何）或 `src/l1/op2_pack.py`（纯结果）  
**核心依赖**：pyNastran `read_op2_geom` / `read_op2`

**含嵌入几何（PARAM,POST,-1）— op2_geom_pack.py**

调用 `read_op2_geom()` 读取包含 GEOM1/GEOM2 表的 OP2 文件，获得与 BDF 接口相同的模型对象（`.nodes`/`.elements`/`.properties`），复用 `bdf_pack._pack_model()` 写入几何 HDF5，随后调用 `op2_pack` 路径提取结果部分。一次运行完成几何与结果的完整提取。

**纯结果（PARAM,POST,-2）— op2_pack.py**

前提条件：BDF 几何已提取（manifest.db 已有 `instances` 表记录，geometry HDF5 已就绪）。

处理步骤：

1. 读取 manifest.db 获取节点标签排序数组（用于将 OP2 中的 GID 映射到 geometry h5 中的行号）；
2. 调用 pyNastran `read_op2()` 加载结果对象；
3. 识别子工况（subcase）分析类型（analysis_code），映射为统一步骤类型：

   | analysis_code | 步骤类型 |
   |---|---|
   | 1（静力）、9（非线性静力） | STATIC |
   | 2（模态，SOL 103） | FREQUENCY |
   | 5、6（频率响应/瞬态） | DYNAMIC |
   | 7、8（屈曲） | BUCKLE |

4. 提取位移结果（`displacement_real`/`eigenvectors`），按行号重排对齐 geometry 中的节点顺序，写入 `l1/results/<result_group>/SUBCASE_<n>__U.h5`；
5. 更新 manifest.db 的 `steps`/`frames`/`result_files`/`result_blocks`/`result_group_meta` 表。

#### 5.2.5 统一输出结构

所有格式提取完成后，workspace 目录结构如下（L2 及以上层统一读取此结构）：

```
workspace/
├── manifest.db                           — 路由索引（SQLite）
└── l1/
    ├── assembly.h5                       — 实例列表、变换矩阵、装配集
    ├── geometry/
    │   ├── <inst>.h5                     — 节点坐标、角节点连接（per-instance）
    │   └── <inst>_highorder.h5           — 完整高阶连接（高阶单元存在时）
    ├── sets/
    │   └── sets.h5                       — 节点集/单元集成员关系
    └── results/
        └── <result_group>/
            └── <step>__<field>.h5        — 多帧结果 [num_frames, N, n_comp] float32
```

**manifest.db 核心表**：

| 表名 | 关键字段 | 说明 |
|---|---|---|
| `instances` | `instance_name, part_name, geom_path, bbox, node_count, elem_count` | 实例路由，L3 按实例名查几何路径 |
| `element_type_dist` | `instance_name, elem_type, count, n_corner_nodes` | 单元类型分布，用于 L2 三角化规则选择 |
| `steps` | `step_name, procedure, num_frames, nlgeom, result_group` | 分析步元数据，nlgeom 标志供 L3 锁定变形比例 |
| `frames` | `step_name, frame_idx, frame_value, description, result_group` | 帧路由，frame_value 为时间戳或特征值 |
| `result_files` | `step_name, field_name, file_path, components, positions` | 结果文件路由，components 为 JSON 数组（如 `["U1","U2","U3"]`） |
| `result_blocks` | `step_name, field_name, instance_name, position, elem_type, h5_path` | 精细路由，指向 HDF5 内部数据集路径 |
| `result_group_meta` | `result_group, display_name, source_file, created_at` | 结果组展示信息 |
| `user_sets` | `set_name, set_scope, user_set_instances` | 用户自定义集合（L3 唯一写入表） |

### 5.3 L2 预处理模块（`src/l2/ingest.py`）

**工程目标**：将 L1 原始几何数据转换为渲染就绪的 GPU 缓冲格式，建立空间索引结构，所有计算一次性离线完成，L3 服务运行期间对 L2 数据只读。

#### 5.3.1 全局坐标变换

从 `l1/assembly.h5` 读取每个实例的 4×4 坐标变换矩阵，将该实例 `l1/geometry/<inst>.h5` 中的局部节点坐标批量变换为全局坐标：

```
global_coords[i] = transform_matrix @ [x, y, z, 1]ᵀ
```

变换后的全局坐标存入 `l2/geometry/<inst>_render.h5`，同时计算实例级包围盒（AABB）写入 manifest.db `instances.bbox` 字段。

#### 5.3.2 表面提取

**实体单元**：面被恰好一个单元拥有的面为外表面（边界面）。实现方式：

1. 枚举每个单元的所有面（按单元类型确定面拓扑：六面体 6 面、四面体 4 面、楔形体 5 面）；
2. 将每个面的节点标签排序后组合为哈希键；
3. 统计每个哈希键的出现次数，出现 1 次者为外表面（仅属于一个单元），出现 2 次者为内部面（两单元共享，丢弃）；
4. 全程 NumPy 向量化实现，避免 Python 循环，百万单元模型可在数十秒内完成。

**壳单元**：壳单元的所有面均为表面（壳没有"内部"），直接进入渲染缓冲。

**线/点单元**：梁/杆单元提取为线段端点对，质量点提取为单点，分别存入 line_elements 和 point_elements 分组，不参与表面提取流程。

#### 5.3.3 三角化

GPU 只支持三角面，所有多边形面需转换为三角形：

- **三角面（S3/C3D4 等）**：直接通过，无需分割；
- **四边形面（S4/C3D8 外表面等）**：沿对角线劈分为 2 个三角形（indices [0,1,2] + [0,2,3]），采用 NumPy 切片广播一次性完成全部四边形；
- **高阶单元**：仅使用前 N_corner 个角节点，中节点丢弃，高阶几何精度损失在工程许可范围内（节点坐标已用于提高积分精度，渲染误差不影响结果判读）。

#### 5.3.4 索引几何构建

相较于 Triangle Soup（每面 3 个独立顶点，无共享），索引几何在同一单元面内共享顶点：

- `positions [Nv, 3] float32`：顶点坐标数组，Nv = 去重后顶点数
- `indices [Nt, 3] int32`：三角形顶点索引数组，Nt = 三角形数
- 顶点间共享范围：同一单元面内共享；不同单元面之间不共享（保留跨面不连续法线，用于平面着色）

顶点法线不存储，由前端 Three.js 的 `geometry.computeVertexNormals()` 按需计算，节省传输带宽。

与每个顶点一起存储的 `vtx_node_row [Nv]` 数组记录该顶点对应 L1 HDF5 中的节点行号，供 L3 结果着色时直接索引结果数组。

#### 5.3.5 特征边提取

特征边是渲染中用于显示模型轮廓与折角的关键视觉元素，分两类：

- **边界边**：仅属于一个三角面的边（在表面的轮廓线上），体现模型外轮廓；
- **折叠边**：相邻两个三角面法线夹角 ≥ 30° 的共享边，体现几何折角（如加强筋、翻边）。

实现采用 NumPy 向量化：构建边-三角面关系哈希表，统计每条边的邻面数量与法线差值，一次扫描完成两类特征边的识别。

特征边端点坐标存入 `l2/geometry/<inst>_render.h5` 的 `feature_edges/positions` 数据集，前端渲染为线框叠加在表面网格上。

#### 5.3.6 八叉树空间索引

用于支持 L3 包围框查询（BBox Select）时的空间粗筛：

- 以包围盒 [xmin,ymin,zmin,xmax,ymax,zmax] 为分割依据，递归八等分空间；
- 参数：`max_depth=8`（最大递归深度）、`leaf_threshold=1000`（叶节点面数上限）；
- 存储格式：扁平数组（`node_bbox`、`node_children`、`node_is_leaf`、`face_indices`、`leaf_offsets`），L3 启动时加载到 `ModelIndex.octree` 内存字典；
- 查询时：从根节点出发，仅递归与查询框相交的子节点，最终返回候选面集合，再经精确 AABB 判断得到命中面。

#### 5.3.7 L2 输出结构

```
workspace/
└── l2/
    ├── render/
    │   └── <inst>_render.h5          — 逐实例渲染缓冲
    │       ├── positions [Nv, 3]     — 顶点坐标 float32
    │       ├── indices   [Nt, 3]     — 三角索引 int32
    │       ├── vtx_node_row [Nv]     — 顶点→节点行号 int32
    │       ├── render_source_elem_row [Nt] — 三角→单元行号 int32
    │       ├── source_elem_etype [Nt]— 三角→单元类型 bytes
    │       ├── feature_edges/        — 特征边坐标
    │       ├── line_elements/        — 梁/杆端点
    │       ├── point_elements/       — 质量点坐标
    │       ├── octree/               — 八叉树扁平数组
    │       └── averaging/            — 单元均化域数据（平滑着色用）
    └── geometry/                     — （备用，当前与 render 合并）
```

### 5.4 L3 服务模块（`src/l3/`）

**工程目标**：以 HTTP REST API 形式按需提供几何与结果数据，支持多项目并发访问，在大规模数据量下保持低延迟响应。

#### 5.4.1 服务架构

**进程模型**：

```
主进程（pre-fork 阶段）
    │── _bootstrap_registry()         ← 加载所有就绪项目的内存索引
    │── fork × N_worker
    ├── Worker 1
    │     ├── FastAPI ASGI 处理请求
    │     └── daemon: registry-poll（10 s）
    ├── Worker 2  …
    └── Worker N

嵌入式 Runner（Linux 默认，仅一个 Worker 持锁）
    └── L1/L2 管线调度（轮询 registry.db，执行 subprocess）
```

**内存注册表（ModelIndex）**：每个就绪项目对应一个 `ModelIndex` 实例，预加载以下数据：

| 字段 | 类型 | 内容 | 用途 |
|---|---|---|---|
| `coords_global` | `{inst: [N,3] float32}` | 全局顶点坐标 | BBox 查询时 AABB 精确判断 |
| `render_indices` | `{inst: [Nt,3] int32}` | 三角索引 | 几何分块传输 |
| `vtx_node_row` | `{inst: [Nv] int32}` | 顶点→节点行号 | 结果着色、拾取结果值 |
| `render_source_elem_row` | `{inst: [Nt] int32}` | 三角→单元行号 | 拾取后反查单元标签 |
| `source_elem_etype` | `{inst: [Nt] S8}` | 单元类型字节串 | L1 HDF5 路径构建 |
| `source_node_rows` | `{inst: [Nt,3] int32}` | 每三角的三节点行号 | 平滑着色结果插值 |
| `octree` | `{inst: dict}` | 八叉树扁平数组 | BBox 查询粗筛 |
| `averaging_data` | `{inst: dict}` | 均化域、邻接角度 | 平滑/平面着色控制 |

所有字段在 `_bootstrap_registry()` 中预 fork 加载完毕，Gunicorn fork 后 Worker 以 copy-on-write 共享物理内存页，查询时不触发页面复制（只读访问），多 Worker 并发服务单项目的内存开销与单 Worker 相当。

#### 5.4.2 API 端点总览

**项目管理**

| 端点 | 方法 | 说明 |
|---|---|---|

#### 5.4.3 结果着色计算

`/results/frame-colors` 端点的计算流程：

1. 从 manifest.db 查询目标字段的 HDF5 路径和数据位置（position）；
2. 从 L1 HDF5 读取该帧结果数据切片 `data[frame_idx]`（单次 IO，[N, n_comp] float32）；
3. 按 component 参数提取标量值（分量提取或 Mises 计算）；
4. 按着色模式（smooth/flat）映射到顶点：
   - **平滑模式**：`values_per_vertex[v] = result_data[vtx_node_row[v]]`（节点级结果直接索引）；
   - **平面模式**：每三角形内三顶点取同一单元值（通过 `render_source_elem_row` 索引单元结果后展开）；
5. 按图例区间线性映射到 [0,1]，通过色表（Rainbow/Jet/Coolwarm 等）转换为 RGBA uint8；
6. 以 L3BE 二进制协议打包返回 `color_per_vertex [Nv*3, 4] uint8`（每三角各独立顶点着色，支持平面着色无共享）与 `legend_range [2] float32`。

#### 5.5.6 模态动画

频率分析振型（`FREQUENCY` 步骤）支持两种动画模式：

**GPU 着色器模式（默认）**

1. GET `/api/odb/{id}/modal/displacement` → 实部 Re 与虚部 Im 位移向量（Float32Array）；
2. 创建自定义 `ShaderMaterial`，将 Re/Im 写入顶点属性（`attr_re`/`attr_im`）；
3. 顶点着色器按 `d = Re·cos(ωt) + Im·sin(ωt)` 计算变形坐标，t 通过 `uniform float u_time` 每帧更新；
4. `requestAnimationFrame` 循环仅更新 `uniforms.u_time.value`，GPU 自行计算每顶点位置；
5. CPU 完全不参与动画计算，帧率稳定 60 fps 与模型规模无关。

**CPU 预计算模式（备用）**

1. 预先计算 N 帧（默认 60 帧/周期）的完整顶点坐标数组 Float32Array[]；
2. 动画循环按帧序号将对应坐标推送到 GPU `position` attribute；
3. 内存占用 ≈ Nv × 3 × 4 字节 × N 帧，百万顶点模型约需 720 MB（60 帧），适合中小型模型。

## 六、关键技术

### 6.1 多格式统一归一化技术

**工程难点**

Abaqus 与 Nastran 的单元定义规范存在系统性差异：单元类型命名体系不同（Abaqus 按材料/形状命名，Nastran 按连接关系命名）；坐标系约定不同（Nastran 支持多参考坐标系，Abaqus 装配中各实例有独立变换）；结果数据组织方式不同（Abaqus 按 Step/Frame/FieldOutput 三层树，Nastran 按 SOL/Subcase/Result 三层树）。直接在 L3 层按格式分支处理会导致代码爆炸，维护成本极高。

**技术路线**

在 L1 提取层建立统一内部表示：

- **单元类型归一化**：BDF/OP2 提取时，按预定义映射表将 Nastran 卡名转换为 Abaqus 等效类型名称，所有后续处理（三角化规则、面拓扑、结果路径）均按 Abaqus 类型名执行；
- **坐标系归一化**：所有实例坐标在 L2 变换至全局坐标系，L3 只需处理全局坐标；
- **结果组织归一化**：Nastran Subcase 映射为 Abaqus Step，SOL 类型映射为 procedure（STATIC/FREQUENCY/DYNAMIC/BUCKLE），帧序号（increment 或模态阶数）映射为 frame_idx，HDF5 存储结构与 ODB 路径完全一致；
- **manifest.db 作为统一路由索引**：所有格式提取后均更新 manifest.db，L3 通过 manifest.db 查询结果文件路径，无需关心格式来源。

**形成能力**

新增数据源格式时，仅需实现一个 L1 提取器（写入统一 HDF5 + manifest.db 结构），L2/L3/前端零改动；现有格式的 bug 修复与优化对其他格式无影响。

### 6.2 二进制载荷协议（L3BE）

**工程难点**

大规模 FEM 模型单帧着色数据量可达数百 MB（千万顶点 × 4 字节 RGBA），若使用 JSON 序列化（Base64 编码），数据体积膨胀约 33%，序列化/反序列化 CPU 开销不可接受，传输时间在局域网内亦达数秒。

单个 API 响应通常需要携带多种类型的数组（float32 几何、int32 索引、uint8 颜色、float32 图例），需要一种轻量的多段打包格式。

**技术路线**

设计固定头部的二进制信封格式（L3 Binary Envelope，L3BE）：

```
L3BE 格式：
  [4B] 魔数 / 版本标识
  [4B] 段数量 N
  对每段：
    [2B] 名称长度 L
    [L B] 名称字节串（UTF-8）
    [1B] dtype 编码（0=float32, 1=int32, 2=uint8, ...）
    [4B×ndim] shape 数组
    [sizeof(dtype) × prod(shape) B] 数据体（C-contiguous）
```

服务端用 NumPy `ndarray.tobytes()` 零拷贝序列化，HTTP `Content-Type: application/octet-stream`；前端 JavaScript 按固定偏移解析 `ArrayBuffer`，重建各命名 TypedArray（`Float32Array`/`Int32Array`/`Uint8Array`），无需任何第三方依赖。

GZip 中间件（`GZipMiddleware`，阈值 1000 字节）对响应自动压缩：几何数据（索引整数）压缩率约 3-5×，颜色数据压缩率约 2×，有效降低带宽需求。

**形成能力**

单次 HTTP 响应携带几何（positions）、索引（indices）、颜色（color_per_vertex）、图例（legend_range）等多段异构数组，避免多次往返；千万顶点级数据从服务端到前端展示的端到端延迟（局域网）在 2 秒内。

---

### 6.3 预处理索引几何与向量化表面提取

**工程难点**

ODB/BDF 存储的是完整体网格（含内部面），渲染只需可见外表面，且 GPU 仅接受三角面。对百万单元模型，若逐单元逐面枚举判断内外，Python 循环耗时数小时。混合单元类型（壳/实体/高阶）的三角化规则各异，高阶单元退化至线性表示需保证拓扑正确性。

**技术路线**

L2 ingest.py 全程使用 NumPy 向量化：

1. **面哈希表**：将所有单元的面拓扑用 NumPy 数组批量展开为 `[total_faces, max_nodes_per_face]`，每行排序后（`np.sort`）作为哈希键，`np.unique` 统计出现次数，O(F log F) 完成全部面的内外判断；
2. **三角化广播**：四边形按 `np.stack([face[:, [0,1,2]], face[:, [0,2,3]]], axis=1)` 一次广播完成全部劈分，无 Python 循环；
3. **高阶退化**：高阶连接数组取前 `n_corner` 列，NumPy 切片操作，无循环；
4. **索引几何去重**：用 `np.unique(..., axis=0, return_inverse=True)` 对展开后的面顶点去重，构建 `positions` + `indices`。

**形成能力**

百万量级单元模型的 L2 预处理在分钟级内完成（实测：100 万 C3D8R 单元约 3 分钟，含八叉树构建）；输出索引几何内存占用约为 Triangle Soup 格式的 1/3 ～ 1/2。

### 6.4 BVH 加速空间查询

**工程难点**

Three.js 原生 Raycaster 对每个 Mesh 做 O(N) 线性遍历，千万三角面模型单次点击拾取需 CPU 遍历全部三角面，耗时数秒，无法满足交互要求。

**技术路线**

集成 `three-mesh-bvh` 库（Bounding Volume Hierarchy，层级包围体树）：

- 几何加载后调用 `geometry.computeBoundsTree()`，以 SAH（Surface Area Heuristic）策略构建 BVH，时间成本为一次性（加载阶段，约 1-2 秒/实例），此后永驻内存；
- 重写 `THREE.Mesh.prototype.raycast` 为 BVH 加速版，O(log N) 时间复杂度；
- 服务端配合内存 `render_source_elem_row` 数组，O(1) 将 Three.js 返回的渲染面索引反查为 ODB 单元行号，再以单元行号从 L1 HDF5 读取精确结果值。

包围框选择（BBox Select）的服务端侧：用内存中的 `octree` 结构（L3 启动时加载）对查询 AABB 进行空间粗筛，将候选面集合压缩至数百/数千量级，再精确判断。

**形成能力**

大规模模型（1000 万三角面）单次点击拾取 < 100 ms 端到端响应时间；框选操作在合理选框范围内 < 500 ms。

### 6.5 多 Worker 内存共享与并发安全

**工程难点**

生产环境 Gunicorn 启动多个 Worker 以利用多核 CPU 并发处理请求。若每个 Worker 独立从 HDF5 加载内存索引，单 ODB 约 2 GB 索引数据 × N 个 Worker 将导致内存占用成倍增长（4 Worker × 2 GB = 8 GB），不可接受。

HDF5 与 SQLite 均有单写者约束，多进程并发写入会破坏文件一致性。

**技术路线**

利用 Linux `fork()` 的 Copy-on-Write（CoW）语义：

1. `_bootstrap_registry()` 在 Gunicorn 主进程（pre-fork 阶段）完成所有就绪项目的 HDF5 读取与 `ModelIndex` 构建，数据写入主进程内存；
2. Gunicorn `fork()` 子 Worker 时，操作系统将主进程内存页标记为 CoW；Worker 以只读方式访问这段内存时，不触发页面复制，所有 Worker 实际共享同一物理内存；
3. L3 服务路径对 HDF5 和 manifest.db 只读（读操作无副作用，不触发 CoW）；user_sets 写入通过 SQLite WAL 模式保证多写者安全；
4. 嵌入式 Runner 通过 `runner_lock` 表在多 Worker 间竞争单进程锁，确保 L1/L2 子进程调度仅由一个 Worker 执行。

**形成能力**

4 Worker 并发服务单个 ODB 的内存开销与单 Worker 相当（≈ 2 GB），支持高并发前端访问而不成比例增长内存。

### 6.6 模态振型 GPU 着色器动画

**工程难点**

频率分析振型动画要求 ≥ 30 fps（流畅体感）。逐帧从服务端请求变形位置数据需承受网络往返延迟（局域网 10 ms、广域网 50-200 ms），无法实现高帧率；CPU 逐帧计算全量顶点坐标并上传 GPU 在大规模模型下 CPU 成本极高。

**技术路线**

**GPU 着色器模式**：谐波振动的数学形式 `d(t) = Re·cos(ωt) + Im·sin(ωt)` 是可并行化的逐顶点计算，天然适合在顶点着色器中执行：

1. 服务端一次返回实部位移向量 `Re [Nv, 3]` 与虚部位移向量 `Im [Nv, 3]`（针对复特征值模态）；
2. 将 Re/Im 写入 Three.js `BufferGeometry` 的自定义顶点属性（`attr_re`/`attr_im`）；
3. 自定义 `ShaderMaterial` 顶点着色器（GLSL）：

   ```glsl
   attribute vec3 attr_re;
   attribute vec3 attr_im;
   uniform float u_time;
   uniform float u_omega;
   void main() {
     vec3 d = attr_re * cos(u_omega * u_time)
            + attr_im * sin(u_omega * u_time);
     gl_Position = projectionMatrix * modelViewMatrix
                   * vec4(position + d, 1.0);
   }
   ```

4. `requestAnimationFrame` 循环仅执行 `uniforms.u_time.value += dt`，每帧 CPU 负担 < 1 ms。

每秒所有顶点的计算在 GPU 中并行完成，帧率与模型规模无关，稳定在显示器刷新率（60 fps）。

**形成能力**

任意规模振型动画 60 fps 流畅播放；振型切换仅需一次 API 请求（更新 Re/Im 属性），响应延迟 < 200 ms（局域网）。

## 七、技术路线

本平台从多格式 FEM 原始文件到浏览器交互后处理，形成以下五步闭环技术路线：

### 第一步：格式适配与忠实提取

针对各求解器格式的异构性，在 L1 层建立专用提取器，将原始数据忠实转换为统一内部表示，不丢失精度，不引入坐标变换：

- Abaqus INP → `src/inp/` 纯 Python 解析器完成词法/语法分析，`inp_pack.py` 写入 HDF5；
- Abaqus ODB → `abaqus_dump.py`（Abaqus Python 2.7）完成有许可证侧的 odbAccess 调用，`l1_pack.py`（Python 3）完成打包，两阶段设计将许可证依赖严格隔离在 Phase 1；
- Nastran BDF → `bdf_pack.py`（pyNastran）读取并按映射表归一化单元类型，免许可证；
- Nastran OP2 → `op2_geom_pack.py`（含嵌入几何）或 `op2_pack.py`（纯结果），按 analysis_code 映射步骤类型，与 ODB 结果路径完全一致。

L1 完成后，所有格式的数据均通过 manifest.db 统一路由，L2 及以上层无需知道数据来自何种格式。

### 第二步：离线渲染缓冲预构建

针对大规模几何数据实时服务的矛盾，将计算密集型操作（表面提取、三角化、空间索引）全部转移至离线预处理阶段：

`ingest.py` 依序执行：全局坐标变换 → 向量化表面提取 → NumPy 三角化 → 索引几何构建 → 特征边计算 → 八叉树构建。

预处理结果持久化为 L2 HDF5 文件，L3 服务期间只读。预处理为一次性成本（项目生命周期内执行一次），不占用实时服务路径的计算资源。

### 第三步：服务层内存索引预加载

针对多 Worker 并发与大规模内存索引的矛盾，在 Gunicorn pre-fork 阶段完成所有就绪项目的内存索引加载：

`_bootstrap_registry()` 读取所有就绪 workspace 的 L2 HDF5，构建 `ModelIndex`（坐标、拾取映射、八叉树等），在主进程内存布局完成后 fork Worker。Worker 以 CoW 共享只读内存，物理内存开销与单 Worker 等同。

注册表轮询线程（10 s 间隔）持续感知新就绪项目，热加载无需服务重启。

### 第四步：二进制协议按需服务

针对大体量数组的网络传输瓶颈，使用 L3BE 二进制协议替代 JSON：

前端按需发起 API 请求（几何首次加载、云图切换、变形显示、拾取等），服务端按请求类型从 L2 HDF5（几何）或 L1 HDF5（结果）读取数组切片，经 L3BE 打包后以 `application/octet-stream` 返回，GZip 中间件自动压缩。

几何数据仅首次加载时传输，后续云图切换仅传输颜色属性（数据量约为几何的 1/6）。

### 第五步：GPU 渲染与交互后处理

针对大规模模型在浏览器中的渲染与交互需求，充分利用 GPU 并行计算能力：

- Three.js WebGL 渲染：所有几何数据驻留 GPU，色彩更新通过 attribute 差量更新实现，不触发几何重传；
- BVH 加速拾取：O(log N) 射线检测，大规模模型拾取响应与小模型无差；
- 模态振型着色器：Re/Im 属性写入 GPU，`requestAnimationFrame` 仅更新时间 uniform，60 fps 动画全程 GPU 计算，CPU 占用 < 1%。

五步技术路线形成从多格式原始文件到浏览器三维交互后处理的完整闭环，各步职责明确，数据单向流动：L1 承担格式归一化与许可证隔离，L2 承担计算密集离线预处理，L3 承担轻量按需服务，前端承担 GPU 渲染与用户交互。

### 9.6 常见问题

**Q：服务启动后浏览器连接正常，但切换云图时报 503 错误**

A：L2 预处理仍在进行中（`geom_status = l2_running`），等待 L2 完成后（状态变为 `ready`）重试。大型模型 L2 处理可能需要数分钟至数十分钟。

**Q：ODB 提取失败，日志显示 odbAccess ImportError**

A：`abaqus_dump.py` 必须通过 `abaqus python` 命令启动，不能用系统 Python 执行。检查 `ABAQUS_CMD` 配置是否指向正确的 Abaqus 安装路径。

**Q：BDF 项目提交后状态长期停留在 l1_running**

A：检查 BDF 文件中是否含有 pyNastran 不支持的卡类型，查看 job_runner 日志（`data/<project_id>/logs/`）获取详细错误信息。

**Q：OP2 结果追加失败，提示"节点数不匹配"**

A：OP2 结果文件与 BDF 几何文件来自不同批次的 Nastran 运行，GID 节点集合不完全一致。确保几何（BDF）与结果（OP2）来自同一版本的模型文件。

**Q：浏览器中模型渲染正常，但拾取无响应**

A：检查浏览器控制台，确认 BVH 构建是否完成（`computeBoundsTree()` 调用在大型模型上可能需要 2-5 秒）。若长时间无响应，考虑升级浏览器版本或启用硬件加速。
