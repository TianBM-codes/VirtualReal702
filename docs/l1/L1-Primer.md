# 小白版：L1 到底是在干什么

## 这份文档是给谁看的

这份文档是给“还不懂 ODB、也不懂有限元实现细节，但想弄明白 L1 在项目里到底干嘛”的人看的。

它不会讲太多专业术语，也不会讲复杂算法。

它只回答一个问题：

**L1 为什么存在，它到底产出什么，它和后面的 L2/L3 是什么关系。**

---

## 1. 先一句话说 L1

L1 做的事情可以粗暴理解成：

**把 Abaqus 的 ODB 原始文件，拆开、整理、保存成我们自己的可读取格式。**

也就是：

- ODB 原始文件不好直接给后端随便查
- 所以先把它转成我们能稳定读取和处理的数据

L1 是整个系统的数据底座。

---

## 2. 为什么不能直接拿 ODB 干活

因为 ODB 是 Abaqus 自己的结果文件格式。

它的问题不是“不能读”，而是：

- 读取环境特殊，通常要依赖 Abaqus
- 数据组织方式是给 Abaqus 用的，不是给你后端服务直接高频查询用的
- 后面如果前端频繁请求，直接从 ODB 里临时到处翻，会很麻烦，也不稳定

所以 L1 的目的就是：

**先把 ODB 里真正有用的东西，完整、忠实地倒出来。**

你可以把它想成“解包”和“转存”。

---

## 3. L1 最核心的原则是什么

L1 最重要的原则不是“聪明”，而是：

**忠实。**

也就是说，L1 不应该在这个阶段做太多自作主张的加工。

它更像是在说：

- ODB 里有什么，我就尽量原样保留下来
- 我先把它变成好存、好读、好索引的格式
- 但我不在这一步做前端显示优化

所以 L1 不是“渲染层”，而是“原始数据层”。

---

## 4. L1 里到底存什么

你可以把 L1 理解成把 ODB 里的东西分成几大类存下来：

### 4.1 模型结构

比如：

- 有哪些实例 `instance`
- 每个实例属于哪个 part
- 实例有没有变换矩阵

这部分相当于“装配结构”。

### 4.2 几何与拓扑

比如：

- 节点编号
- 节点坐标
- 单元编号
- 单元连接关系

这部分相当于“模型骨架”。

### 4.3 集合

比如：

- 节点集合
- 单元集合
- 装配集合

这部分相当于“模型分组信息”。

### 4.4 材料与截面

比如：

- 材料名
- 截面名
- 截面对应哪个单元集合

这部分相当于“工程属性”。

### 4.5 结果数据

比如：

- 位移 `U`
- 应力 `S`
- 应变 `E`
- 每个 step / frame 下的结果

这部分相当于“分析结果本体”。

---

## 5. L1 不做什么

这个很重要。

L1 **不做**下面这些事：

- 不做前端显示壳子
- 不做表面提取
- 不做三角化
- 不做法向计算
- 不做云图颜色映射
- 不做变形显示用的最终渲染 buffer

这些都不是 L1 的事。

如果把这些混进 L1，后面会很乱。

所以你可以简单记：

**L1 负责“把原始分析数据拿出来”，不负责“把它变成浏览器画面”。**

---

## 6. L1 和 L2 的关系是什么

可以这样理解：

- L1 像原材料仓库
- L2 像加工车间

L1 先把 ODB 里的原始东西整理好放进去。

然后 L2 再从 L1 里拿数据，做：

- 表面提取
- 三角化
- 建立显示壳子
- 建立显示面片和原始单元/节点的映射

所以：

- L1 偏“原始数据”
- L2 偏“显示预处理”

---

## 7. L1 和 L3 的关系是什么

L3 是运行时服务层，它面对的是前端的各种请求。

比如前端会问：

- 这一帧的位移结果是什么
- 这个面片点中了哪个单元
- 这个集合对应哪些面片
- 这个 field 当前值怎么取

L3 之所以能回答这些问题，是因为：

- L2 给了它“显示壳子和映射关系”
- L1 给了它“原始语义和原始结果”

所以 L1 对 L3 的价值是：

**当 L3 想知道“这个显示对象背后真正的工程信息是什么”时，它要回到 L1 里查。**

---

## 8. 为什么 L1 要尽量一次性做完

因为 L1 做的事情比较重，而且依赖特殊环境。

比如：

- 需要 Abaqus 环境
- 需要读取 ODB
- 需要遍历很多原始对象

这类事情不适合每次前端点一下就重新做。

所以正确方式就是：

- ODB 上传后
- L1 跑一次
- 把结果落盘
- 后面就尽量不要重复从 ODB 原文件里直接抠

这就是“离线预处理”的思路。

---

## 9. L1 产物为什么要存成 HDF5 和 SQLite

你可以先用很朴素的方式理解：

### 9.1 HDF5

适合存大数组。

比如：

- 节点坐标
- 单元连接
- 多帧结果数据

这些东西本质上都是大块数组，HDF5 很适合。

### 9.2 SQLite

适合存“索引和目录”。

比如：

- 某个结果在哪个文件
- 某个 step 有几帧
- 某个 set 对应哪条路径

这些不是大数组，而是查表信息，SQLite 很适合。

所以这两个搭配起来就是：

- HDF5 存大数据
- SQLite 存定位信息

---

## 10. L1 转存后的目录结构大概长什么样

你不用先记所有文件名，只要先建立一个感觉：

L1 转存完之后，通常会变成一个“工作区目录”，里面把不同类型的数据分开放。

大概像这样：

```text
/data/<odb_id>/
├── manifest.db
└── l1/
    ├── assembly.h5
    ├── geometry/
    │   ├── <instance>.h5
    │   └── <instance>_highorder.h5
    ├── sets/
    │   └── sets.h5
    └── results/
        ├── <step>__<field>.h5
        ├── <step>__<field>.h5
        └── ...
```

你可以把它粗暴理解成：

- `assembly.h5`
  存整个装配层面的信息

- `geometry/<instance>.h5`
  存某个实例的节点、单元、连接关系、材料、截面、实例内集合

- `sets/sets.h5`
  存各种集合，尤其是跨层次整理后的集合数据

- `results/<step>__<field>.h5`
  存某个分析步骤下某个结果场的大数组

- `manifest.db`
  存“目录索引”，告诉系统去哪里找这些数据

### 10.1 为什么按这种方式拆

这样拆不是为了好看，而是为了后面更好查。

比如：

- 你要查几何，不需要把结果文件也一起打开
- 你要查某个 field，不需要把所有 field 都扫一遍
- 你要查某个 instance，可以直接进对应文件

这本质上是在做“按用途拆箱”。

---

## 11. 这样设计的好处是什么

这个目录结构和存储方式的核心好处，是让后面的 L2 和 L3 都更轻松。

### 11.1 好处一：职责清楚

不同数据放在不同位置：

- 装配信息一类
- 几何信息一类
- 集合信息一类
- 结果信息一类

后面的人一看就知道去哪里拿数据。

### 11.2 好处二：避免反复扫大文件

如果所有东西都混在一起，查询时就很容易：

- 打开一个超大文件
- 到处翻
- 每次都重复定位

现在拆开之后，能更直接定位。

### 11.3 好处三：方便 L2 做预处理

L2 最关心的是：

- 节点
- 单元连接
- 表面面
- 实例变换

这些都能直接从几何和装配相关文件拿，不必被结果数据干扰。

### 11.4 好处四：方便 L3 做查询

L3 最关心的是：

- 当前 field 在哪里
- 某个 set 在哪里
- 某个 instance 的 labels 和 rows 怎么对应

`manifest.db + HDF5` 的组合，就是为了让 L3 可以“先查目录，再切数组”。

### 11.5 好处五：更适合大模型

模型大了之后，最怕的不是“有没有数据”，而是：

- 数据太大，不能乱扫
- 不同请求读到的数据范围差很多

按目录和类型拆开，后面更容易做：

- 分文件读取
- 按需打开
- 按帧切片
- 按实例查询

### 11.6 好处六：便于后续扩展

如果以后要补新内容，比如：

- 新的结果场
- 新的集合类型
- 新的高阶单元信息

通常只要往对应区域补，不至于把整体结构搅乱。

---

## 12. L1 里最值得你记住的几个对象

如果你现在不想看太多细节，先记住这些就够了。

### 10.1 instance

装配里的一个零件实例。

很多节点和单元编号只在 instance 内唯一。

### 10.2 node

节点，空间中的点。

有：

- label
- 坐标

### 10.3 element

单元，由多个节点组成。

有：

- label
- 类型
- 连接关系

### 10.4 step

分析步骤。

### 10.5 frame

步骤里的某一帧结果。

### 10.6 field

结果场，比如：

- `U`
- `S`
- `E`

---

## 13. L1 结果数据长什么样

不用先记实现细节，只需要有这个感觉：

L1 会把结果按一种比较规整的方式存下来，比如：

- 某个 step
- 某个 field
- 某个 instance
- 某个位置类型（比如 NODAL）
- 对应若干帧的大数组

这样做的目的就是：

以后 L3 查询的时候，可以比较直接地说：

- 我要第 10 帧
- 我要这个 instance
- 我要这个字段

然后直接切出来，而不是重新遍历 ODB。

---

## 14. L1 最像什么

如果非要用一个非常俗的比喻：

L1 很像把一份别人专用格式的大型工程档案，拆成你自己系统内部的档案柜。

这个档案柜的特点是：

- 分类清楚
- 查找稳定
- 大文件和目录分开存
- 后面的人都按这个档案柜来查

L2、L3 都是在这个档案柜的基础上继续干活。

---

## 15. L1 做对了，后面有什么好处

如果 L1 做得好，后面会轻松很多。

好处主要有：

- 不用反复读原始 ODB
- 数据结构更稳定
- L2 更容易做预处理
- L3 更容易做快速查询
- 多个 API 不会各自重新发明一套读法

也就是说，L1 做得好，整个系统会稳很多。

---

## 16. L1 做不好，会出现什么问题

如果 L1 设计得差，后面问题会很明显：

- 结果结构混乱
- 同一类数据到处放
- L2 不知道该怎么接
- L3 查询时要扫很多文件
- 前后端讨论时总在问“这个数据到底在哪”

所以 L1 虽然不是前端最直接看到的部分，但它其实是整个系统的地基。

---

## 17. 你现在最需要把 L1 理解到什么程度

你不需要现在就会写 `abaqus_dump.py`。

你只需要把 L1 理解到这个程度就够了：

- 它是 ODB 的忠实转储层
- 它负责把原始分析数据拆出来、存下来
- 它不给前端直接显示
- 它是 L2 和 L3 的数据来源
- 它的价值在于“稳定、完整、可索引”

到这个程度，你就已经比“完全不懂”前进很多了。

---

## 18. 最后一句大白话总结

L1 不是在“做显示”，也不是在“做交互”。

L1 做的事情很朴素：

**把 Abaqus 的 ODB 原始世界，老老实实搬到我们自己的系统里，并且搬得整齐、稳定、后面好查。**

后面的 L2 和 L3，都是建立在这个前提上。
