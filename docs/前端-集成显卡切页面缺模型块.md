# 集成显卡上切页面后模型缺块：排查结论与改法二（切走时释放显存）

记录时间：2026-10-29　状态：**待第三方前端同事在集成显卡机器上实测"重传耗时"**

## 1. 现象

- 同一个模型，有独立显卡的机器显示正常；只有集成显卡的机器上，模型会缺一块。
- 缺的位置不固定：不同菜单页面缺的地方不一样。
- 控制台没有红色报错；`chrome://gpu` 显示 WebGL 为 Hardware accelerated。

## 2. 排查过程与结论

| 怀疑 | 检查 | 结论 |
|---|---|---|
| 后端数据缺失 | 同一后端，有显卡的机器完整；缺的位置会变 | 排除 |
| 软件渲染（SwiftShader）上限 | WebGL 为 Hardware accelerated（集成显卡） | 排除 |
| 深度缓冲精度不足（相机 far/near ≈ 1e6） | Console 中 `gl.getParameter(gl.DEPTH_BITS)` = 24，`getError()` = 0 | 基本排除 |
| **多个页面各自持有一份模型，显存累积** | 前端是后台管理布局（左侧菜单树，右侧每个菜单一个页面组件），页面被缓存（keep-alive）不销毁，每个页面都加载并显示模型；同一画面里有 2 个 WebGL 画布 | **最可能的原因** |

说明：
- 模型窗口在 iframe 里，直接在 Console 里查 `canvas` 会得到 `[]`。要先把 Console 顶部的 `top` 下拉框切到对应的 iframe。
- `getError()` 读一次就会清空，返回 0 只代表读的那一刻没有错误，不能证明之前没有分配失败。

**结论**：这是前端问题。客户要求切页面要快，所以切走的页面不释放显存。集成显卡和系统共用内存、显存有限，几个页面叠加后部分缓冲区分配失败，对应的模型块就画不出来。后端数据是完整的，后端改不了这一点。

**已否决的方案**：
- 所有页面共用一个三维视图（改法一）：工作量太大。
- 切走时销毁整个页面：不满足"切页面要快"的要求。

## 3. 改法二：切走时只释放显卡那份，切回来自动重传

three.js 的 `geometry.dispose()` 只释放显卡上的缓冲区。浏览器内存里的顶点数组、算好的法线和拾取用的 BVH 都还在，下次渲染时 three.js 会自动重新上传。

所以切回来时不用重新下载，也不用重新计算，只多一次"上传到显卡"。第一次打开慢，主要慢在下载、解析、算法线、建 BVH 这些 CPU 上的工作，上传本身应该快得多，但要实测确认。

```js
import { onActivated, onDeactivated } from 'vue'

function releaseGpu(root) {
  root.traverse(o => { if (o.geometry) o.geometry.dispose() })  // 网格、边线、线单元都会被遍历到
}

onDeactivated(() => {
  if (lowVram) releaseGpu(scene)
})

onActivated(() => {
  // 不用做任何事，下一帧渲染时自动重传；下面只是用来量时间
  const t0 = performance.now()
  renderer.render(scene, camera)
  requestAnimationFrame(() => requestAnimationFrame(() =>
    console.log('重传耗时 ms', Math.round(performance.now() - t0),
                '显卡中几何数', renderer.info.memory.geometries)))
})
```

### 只在集成显卡上启用

这样独立显卡的行为和现在完全一样。

```js
const gl = renderer.getContext()
const ext = gl.getExtension('WEBGL_debug_renderer_info')
const gpu = ext ? gl.getParameter(ext.UNMASKED_RENDERER_WEBGL) : gl.getParameter(gl.RENDERER)
const lowVram = /Intel|UHD|Iris|Microsoft Basic|SwiftShader|llvmpipe/i.test(gpu)
             && !/NVIDIA|GeForce|Quadro|RTX/i.test(gpu)
```

AMD 核显的型号字符串是 "Radeon Graphics"，跟独立显卡不好区分，需要按客户实际机器补充规则。

### 注意事项

1. **不要**调用 `renderer.dispose()` 或 `forceContextLoss()`，那样会把整个画布销毁。
2. 如果代码里用了 `attribute.onUpload(...)`，在上传后清掉 CPU 上的数组以省内存，那么 dispose 后就无法自动重传。这种情况要么去掉 onUpload，要么不能用这个办法。
3. 网格上如果有 `color` 顶点属性，但材质是 `vertexColors: false`，这个属性完全没用、白占显存，建议删掉。仓库里的 `viewer/src/components/ThreeViewport.vue` 就是这样，第三方前端要对照着看。法线和 uv 也可以改用 `Int16` / `Uint16` 加 normalized，每份模型的显存大约能省一半。
4. 每个页面一个 renderer 就是一个 WebGL 上下文。Chrome 同时最多保留 16 个左右，超过时最早的那个会丢失（触发 `webglcontextlost`）。
5. 建议每次上传模型后检查 `gl.getError()` 是否为 `OUT_OF_MEMORY`，出错时主动释放其他页面再重试，或者给出提示，不要悄悄缺块。

## 4. 下一步

1. 前端同事在集成显卡机器上测"重传耗时"（看上面代码打印的值）。
2. 如果耗时可以接受（例如零点几秒），就只在集成显卡上启用切走释放，然后验证多切几个页面后不再缺块。
3. 如果耗时不能接受，再考虑第 3 点的显存瘦身（去掉无用的 color 属性、压缩法线和 uv），让集成显卡能多留住几个页面。
